# 遅れの通知を1つにまとめて、すぐ知らせる（データ担当・11/13）

PM の指示（11/13 20時20分）・本人「飛行機の遅れが二重にくる時があるので、きちんとまとめて、遅れが発生次第通知が来るようにして」。決定事項【11/13】遅れの通知に従った。

- 変えるファイル：通知の送り手（_shared/alert_push.ts・flight_watch.ts・odpt_status.ts、flight-watch・odpt-status）、新しく _shared/alert_merge.ts・odpt_fast.ts、移行 168 alert_merge
- 手順：お知らせは便ごと・種類ごとの1行のまま書き直せるようにし、通知は「便名＋運航日」で1件にまとめ、送った記録で同じ中身を二度送らない。乗る便だけ毎分見る回を足す
- 確かめ方：関数のテスト（まとめ方・15分と60分・30分ふえたとき・問い合わせの決め方）と SQL のテスト t107、本番の重なりは読むだけの SQL（docs/pm/alert-dup-check.sql）

## 1. 作ったもの

**二重になる所をどう直したか**

| 二重になる所 | 前 | 直したあと |
|---|---|---|
| 出発の遅れと到着の遅れ | 種類が違うので2回届く | 同じ便は1件。2つ目は「30分以上ふえた」ときだけ上書き |
| 推定（flight-watch）のあとに航空会社の運航情報（odpt-status） | 両方届く | 運航情報がはじめて届いたときに、同じ通知を【更新】で上書き（端末では1件のまま） |
| 共同運航・時刻表の重なり（同じ出発・到着・定刻の行が2つ） | 行ごとに届く | 1つの便にまとめ、代表の便名を1つにする。どちらの便名を選んだ人にも1件 |
| 通知の tag が `fw-便名`（日付なし） | 前の日の通知と重なる・上書きのとき鳴らない | `fw-便名@運航日@出発空港` にし、`renotify: true` を付けて送る |
| 空港と乗る便の両方を選んでいる人 | 同じ便で別々に届くことがある | 購読1つ・便1つにつき1件 |
| 空港ごとの通知 | 60分以上の遅れが全部届く | 主要空港の、門限に間に合わないおそれ・0時前後に着く便と、欠航・ダイバート・引き返しだけ |
| flight-watch と odpt-status が同時に動く | 同じ便を両方が送ることがある | 送る前にデータベース（alert_push_claim）で1件ずつ決めて記録するので、どちらか一方だけ |

**送る決まり**（_shared/alert_merge.ts・alert_push_claim）
- 「この便に乗る」（push_subs.flights）の人：15分以上の遅れと、欠航・ダイバート・引き返し
- 空港ごとの通知（push_subs.airports）の人（PM の追記 11/13 20時25分・本人「通知がくるのは主要空港がいいな、門限ギリギリになりそうな便とか0時に着くような便とか」）：「60分以上の遅れ全部」をやめ、選んだ空港が主要空港（羽田・成田・関西・伊丹・中部・新千歳・福岡・那覇）の便で、次のときだけ
  - 門限に間に合わないおそれ：着く空港の運用時間の終わりの30分前より遅く着く見込み。終わりより後なら「出発した空港へ引き返すか、ほかの空港へ向かうことがあります（推定）」まで書く。文の例「伊丹の門限（21時）に間に合わないおそれ：JL139 羽田→伊丹、到着の見込み 20時52分（約65分遅れ）」
  - 0時前後に着く：24時間の主要空港に、定刻は夜（12時〜23時29分）で、遅れ（15分以上）のせいで見込みが 23時30分〜翌1時に入った便。文の例「0時前後に着く見込み：JL529 羽田→新千歳、到着の見込み 23時50分（約45分遅れ）」
  - 欠航・ダイバート・引き返し（主要空港だけにした。主要でない空港の人にも出すかは本人に決めてほしい：3 の4）
  - 到着の見込みは「到着の定刻＋到着の遅れ（なければ出発の遅れ）」。運航情報の時刻なら文の終わりに「（航空会社の運航情報から）」
- 門限（運用時間の終わり）：2026-11-13 に原文を開いて確かめた。伊丹 21時（豊中市「大阪国際空港の現況等」令和8年度資料 https://www.city.toyonaka.osaka.jp/machi/kukou/gaiyou.files/R8siryou.pdf ・AIP JAPAN AD 2.3）、福岡 22時（利用時間 7時〜22時。国土交通省 資料 令和8年9月 https://www.mlit.go.jp/koku/content/002023058.pdf ）、成田 24時（A滑走路。やむを得ない理由なら24時30分まで。千葉県 令和8年8月28日更新 https://www.pref.chiba.lg.jp/kuushin/narita/danryokuka.html ）。ほかの主要空港は24時間（AIP JAPAN 2026年10月1日版。ops_core.js の夜の決まりと同じ）。数は少ないのでコードの定数（CURFEW）で持ち、表は作らない
- 送るのは「はじめて」「門限・0時前後・欠航・ダイバート・引き返しになった（重くなった）」「航空会社の運航情報がはじめて届いた」「送った遅れから30分以上ふえた」ときだけ。それ以外の小さい変化では鳴らさない。ふつうの遅れを送った乗る便の人にも、門限・0時前後になったら送り直す
- 見出し：欠航 → ダイバート → 引き返し → 遅れ。運航情報があれば推定より運航情報。遅れは大きい方の文

**すぐ知らせる**
- 遅れのお知らせは15分から作る（前は60分）。推定の出発の遅れは離陸が定刻の30分後から（地上走行15分を引いて15分）、「まだ飛行中」は到着の定刻の15分後から、30分ふえるごとに出し直す
- 新しく odpt-status?fast=1 を毎分（cron odpt-status-fast）：「この便に乗る」で選ばれた便だけ、出発前は出発空港の出発情報、出発後は到着空港の到着情報を ODPT に問い合わせる。同じ会社・空港・向きは1回、1回に6件まで、50秒に1回だけ。選ばれた便がなければ問い合わせない
- ODPT への問い合わせの回数の目安：今の5分ごとの回は1回4件（4分に1回まで）＝1日約1,150件。毎分の回は選ばれた便があるときだけで、多くて1分6件（1日の上限の目安 8,640件）。ふつうは乗る便の空港の1〜2件。規約は「呼び出し回数などはセンターが制限を決められる・著しい負荷は利用停止」なので、上限の6件で抑えている。送るときは Web Push の urgency を high にした

**移行 168 alert_merge**（先頭に lock_timeout 10s）
- flight_alerts に late（遅れの分）・official（航空会社の運航情報か）・updated_at を足す。今の行は文に「航空会社の運航情報」があれば official
- flight_alerts_put(p)：お知らせを入れる・書き直す。推定で運航情報を上書きしない。service_role だけ
- 表 alert_push_log（購読・便・重さ・遅れ・運航情報か・本文・回数・時刻）：送った記録。RLS 有効・ポリシーなし・anon と authenticated から取り上げ。購読を消すと一緒に消える。3日で消す（cron alert-push-log-cleanup、statement_timeout 30s）
- alert_push_claim(p)：送ってよいものだけを返して記録する（同時に呼ばれても二重にならない）。service_role だけ
- 画面のお知らせの一覧 public.flight_alerts() は今までどおり60分以上の遅れと遅れ以外だけ（返す形も同じ）。急増の見張り（ops.alert_watchdog）と flight-watch の安全装置も60分以上だけを数える（15分からの遅れで誤って止まらないように）
- odpt_status_runs に id 2（毎分の回の時刻）
- 影響：チェックイン（通知の中身と回数。画面は変わらない）。経営は関係なし。航路と機体の記録には触らない

## 4. ほかの担当への依頼
- チェックインへ：src/sw.js の push の受け取り（showNotification）で、届いた中身の `renotify` を渡してほしい（`renotify: !!d.renotify`。tag があるときだけ）。同じ便の通知を上書きするときにも鳴るようにするため。今のままでも重ならず1件にはなるが、上書きのときに音が鳴らない。あわせて、通知の説明の文（「この便に乗る」は15分以上の遅れから、空港ごとの通知は主要空港の門限・0時前後の便と欠航・ダイバートだけ）が要るか、画面案で決めてほしい。主要でない空港を選んでいる人には、空港ごとの遅れの通知が届かなくなる
