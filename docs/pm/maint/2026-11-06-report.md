## 2. 確かめた結果
- t93（29項目）すべて通過：直すのは前からある11本だけ・時刻は今のまま・中身は前の定義と1字ずつ同じ（cron の記録の 1日→8日 だけ違う）・消す先の表も同じ・航路と機体の記録の表を消す文はない・移行に delete／drop／表やポリシー・権限の変更はない・11の文がどれもエラーなく流れて上限が効く・BRIN 索引4つ・候補の日は索引があってもなくても同じ・処理を全部流しても全機の航跡と滑走路の記録は1行も減らない・RLS と権限は今のまま
- SQL のテスト101本すべて通過（cron を読むテストは t92 と t93 だけ）
- 本物の Postgres 16（作業メモリ 64kB）：
  - 上限：`set statement_timeout = '1s'; set lock_timeout = '5s'; select pg_sleep(3)` は1秒で止まり、次のつながりには持ち越さない（0 に戻る）。11本の文は本物でもすべて流れた
  - 移す日の読み出し（day = その日）：主キーを丸ごと 10,137 ページ読む → BRIN で 1,170 ページ（約9分の1、35ms → 2〜9ms）
  - 候補探し（day < 400日前 で日ごとにまとめる）：変わらない（今も主キーの索引だけを読み、表本体は読んでいない。主キー 80MB を全部読む）
  - 正直なところ：今いちばん重いのは「全機の航跡を毎晩丸ごと読んでいる」ではなく「主キーの索引を丸ごと読んでいる」だった。BRIN の効き目は、移す日の読み出し・消す処理と、時刻だけで探す表（滑走路・ゴーアラウンド・管制）で出る
  - 見つけたこと：cold_candidates は、滑走路の記録などで400日より前の行がたくさんあると、日ごとにまとめる並べ替えで一時ファイルを使う（作業メモリ 64kB で 1MB）。今は 400日より前の記録がないので起きない（起きるのは 2027年11月ごろから）。次の回の候補にする

経営の毎晩の処理（co-rank・co-size・co-sky の3本と、SQL で動く co3-* の15本）には時間の上限が付いていない。止まらないとほかの処理や画面を巻き込む。

`set statement_timeout = '…'; set lock_timeout = '5s'; select public.co3_…()` の形に直してほしい（co3-weather-cleanup も含む）。
月の締め（co3-month-close・co3-season-close）は失敗すると次の月まで待つので、上限を長め（10分）にするか、失敗したら翌日もう一度動くようにするかも決めてほしい。
