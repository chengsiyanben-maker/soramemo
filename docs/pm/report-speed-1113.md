## 1. 作ったもの
- **移行 164 `edge_cache`（関数どうしで使い回す置き場）**：key・body（JSON）・at の小さな表。RLS は有効でポリシーなし（anon・authenticated は読めも書けもしない。読み書きは関数＝service_role だけ）。上書きするだけで増えない（約270行・1MB 未満）、消す処理は要らない。fillfactor 70
  - 影響：チェックイン（空港の今・運用の気象通報が速くなるだけ。返す形は同じ）。エアライン経営は使わない
- **airport-now**：便（ODPT）・気象通報・予報を「関数の中の記憶 → 置き場 → 配信元」の順に見る。記憶にないものだけ置き場を1回でまとめて読む。配信元が取れないときは置き場の古い値で返す。Server-Timing に `shared` を足した
- **metar**：同じく置き場を使う。Server-Timing（`shared`・`upstream`）を足した（今までなかった）
- **airport-traffic**（2回目の回で足した）：見る人の呼び出しに Server-Timing（`mem`＝記憶から・`live`＝記録の位置を読んだ・`adsb`＝記録が止まっていて adsb.lol に聞いた・`trails`＝航跡の線を書いた）。中身と返す形は変えない。この関数は記録の処理が30秒ごとに位置を表に入れているので、置き場は足さない
- 共通の部品 `supabase/functions/_shared/edge_cache.ts`、読むだけの SQL `docs/pm/speed-check-1113.sql`

### なぜ効くか
Supabase の関数は呼ばれるたびに別の入れ物（isolate）で動くことが多く、「数分ためて使い回す」記憶はすぐ消えていた。そのため人が少ない時間ほど毎回 ODPT に4回（JAL・ANA × 到着・出発）問い合わせ、遅いと上限の8秒まで待っていた（11/7 新千歳で 13〜20秒）。置き場があれば、どの入れ物でも主キーで1回引くだけ（データベースまで数ミリ〜20ミリ秒）。配信元に問い合わせる回数も減る（ODPT・aviationweather.gov への負担が軽くなる方向で、規約の範囲は今と同じ。ODPT のデータを外に出す形は変えない）。
