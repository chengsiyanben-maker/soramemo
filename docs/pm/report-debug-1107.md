## 1. adsb.lol の 429
### 分かったこと
- 見る人の呼び出し（`airport-traffic?iata=NRT` など）は、20秒の使い回しが**関数の実体ごと**（メモリの中）なので、続けて呼ぶと別々の実体に振られ、そのたびに adsb.lol に問い合わせていた。PM が14空港を続けて呼ぶと、記録の処理（30秒ごとに3回）と合わせて短い時間に十数回になり、429 になる。見る人が増えても同じことが起きる
- 30秒ごとの記録の処理（RECORD）は、円（東・西・北か南）のどれかが 429 になると、その回のその円の機体は live_positions・track_points・reg_legs に残らない（取り直しはしていなかった）。抜けたかどうかは、pg_net に6時間ほど残る記録の処理の返事（`"recorded":{"NRT":"adsb.lol 429"}`）で数えられる → 健康診断の SQL の「4」
- **別の抜けを見つけた（429 とは関係なく、ずっと）**：航跡の点と機体ごとの便の記録は「時刻が偶数の30秒（毎分の前半）」の回だけ残していた。ところが南の円（那覇を中心に、沖縄・奄美・宮古・石垣）は後半の回にしか取らないので、**南の円の機体は航跡の点（track_points）にも便の記録（reg_legs）にもほとんど残っていない**見込み（コードを読んだ結論。本番の数は健康診断の「3」の「南」で確かめられる。1440分のほとんどが抜けていれば当たり）。那覇発着の便の空の道すじ（flight_tracks）・乗った機体の記録も、本州側の区間しか残っていないはず
### 直したもの（PR）
- 見る人の呼び出しは adsb.lol に問い合わせず、記録の処理が live_positions に残した75秒以内の位置から作る（airport-foreign がすでにしているのと同じやり方）。adsb.lol への問い合わせは、見る人の数によらず30秒に3回だけになる。記録が止まっている（75秒以内の位置が日本中に1つもない）ときだけ、前のように adsb.lol に問い合わせる
  - そのために live_positions に進行方向 trk（smallint・0〜359）を足す（移行 156。列を足すだけ、RLS は今のまま、行は消さない）。着陸・離陸の見分けで「ほかの空港へ向かう機体」を除くのに使う
  - 違い：live_positions は便名のある機体だけなので、**便名のない機体（自家用機の一部など）は地図に出なくなる**。位置は最長で約75秒前（北と南の円は1分に1回の取り込み）。返す形は同じ
- 記録の処理で 429・420 のときは、1回だけ待って取り直す（Retry-After があればそれ、最長5秒）
- 南の円の抜け：円ごとに残す回を決める（_shared/traffic.ts の recordPlan）。どの円も航跡の点は1分に1回、便の記録は2分に1回になる（テストで確かめた）
### ほかの案（入れていない）
- 「日本全体を1回で取る」は、adsb.lol の円の半径の上限が250海里なので1回では入らない。今の3回（東・西・北か南）がほぼ最小
- 待って取り直しても続くなら、記録の処理を40秒ごとに延ばす案もある（航跡の点は少し粗くなる）。adsb.lol の作者の返事（11/6 22:24 に連絡済み）で上限が分かってから決めたい

## 2. airport-now が遅い
### 分かったこと
- 天気・予報・便・アメダスのどの問い合わせにも**待つ上限がなかった**ので、いちばん遅い配信元を最後まで待っていた
- 外から測った（11/7 23時ごろ）：aviationweather.gov は Azure の配信網の後ろにあり、ためてある答え（60秒）がないと遅い。新千歳の METAR が 1回目 12.0秒 → 2回目 0.2秒、TAF が 19.1秒 → 0.2秒、鹿児島の TAF は 20秒で 504、松山の TAF は 3.9秒。14空港をまとめた METAR は 0.2秒（運用の記録が5分ごとに同じものを取っている）。**中部の 20.3秒 → 0.6秒は、ちょうどこの「1回目だけ遅い」形**
- airport-now は空港1つずつ METAR と TAF を問い合わせるので、見る人の少ない空港ほど毎回1回目になる。新千歳がいつも遅いのもたぶんこれ（TAF は30分ためるが、関数の実体ごとなので効きにくい）
- ODPT は合言葉がないと測れなかった（合言葉なしで 0.8秒で 403）。1空港あたり4回（JAL・ANA × 到着・出発）を同時に問い合わせている
### 直したもの（PR）
- 待つ上限：ODPT 8秒・aviationweather.gov 5秒・気象庁 4秒。超えたら関数の中の古い値（なければ天気の記録 wx_obs の3時間以内、それもなければ空）で返す。いちばん長くても約8秒
- 返事に **Server-Timing** の見出しを付けた（例 `db;dur=3, metar;dur=420, taf;dur=5003, odpt;dur=7900, total;dur=7905`）。PM が `curl -sI` で叩けば、どこで時間がかかったかすぐ分かる（反映後に新千歳で測ってほしい）
- METAR が空の返事（204）でもエラーにしない
### 決めてほしい案（入れていない。表か処理が増える）
- 案A：天気を先に取っておく。5分ごとに、airport-now が使う全部の空港の METAR と TAF を**まとめて1回**取り、表（例 wx_now：空港・通報・予報・取った時刻。RLS は有効・読むのはサーバーだけ）に置く。airport-now と metar 関数はこの表を読む（数十ミリ秒）。aviationweather.gov への問い合わせも減る
- 案B：便は ODPT に直接問い合わせず、odpt-status が5分ごとに入れている予定の便（flight_schedule の状態・変更後の時刻・搭乗口）から作る。ODPT への問い合わせが1空港4回 → 0回になる。ただしターミナルと航空会社のお知らせの文は今の表にないので、列を足すか、出さないかを決める。画面に出るものが変わるのでチェックイン担当と相談
- おすすめ：まず PR（上限と Server-Timing）を入れて1週間測る → 天気が遅ければ案A、ODPT が遅ければ案B
