# 門限ギリギリの知らせの幅を30分→10分に（データ担当・11/15）

PM の指示（11/15 19時25分）・本人「遅れの通知は着く10分前から通知して」→「門限ぎりぎりになるやつ」。ブランチ data/curfew-10（main 754bca5 から）。本番には入れていない。

## 作ったもの
- `supabase/functions/_shared/alert_merge.ts`：定数 `CURFEW_NEAR` を 30 → 10。門限の判定（nightNotice）はこの1か所だけを見ていて、空港ごとの通知（主要8空港）と「この便に乗る」の通知は同じまとめ（mergeAlerts の rank 2）を使うので、両方が10分になる
- 変えていないもの：門限の時刻（伊丹21時・福岡22時・成田24時）、0時前後（23時30分〜翌1時）、欠航・ダイバート・引き返し、乗る便の15分、30分ふえたら送り直す決まり。表・移行・RLS・cron は変えない（移行なし）
- 影響：チェックイン（通知だけ・画面は同じ）。経営なし

## 確かめた結果
- テスト `supabase/tests/alert_merge_test.ts` に「門限の幅は10分」を足した：伊丹で 11分前は出ない・10分前と9分前は出る・過ぎたら「間に合わない見込み」、福岡・成田も同じ。前の30分の幅なら出ていた25分前は出ないこと、乗る便の人にも門限の文で届くこと、主要空港の人には11分前は届かず9分前は届くことも見る。30分の幅を前提にしていた福岡・成田の古い例は、この新しいテストにまとめた
- deno test（supabase/tests 全部）255本 通過・全関数の型の確認 通過（Deno 2.5.6）

## 本人に決めてほしいこと
- 「反映して」が出たら main に入れる（移行がないので番号の rebase は要らない。関数 alert-push などの公開だけ）
- 門限の「10分前」は見込みの到着の時刻で見ている（推定の到着は数分ずれることがある）。10分前ぎりぎりの便は、推定がずれると知らせが出たり出なかったりする。気になれば、乗る便だけ幅を広げる案も作れる
