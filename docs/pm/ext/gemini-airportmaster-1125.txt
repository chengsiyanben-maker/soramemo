アプリ同梱用の空港マスターデータは、「ライセンスがクリーンで商用配布しやすい公開データ」を選び、端末負荷を抑えるために約100空港の合計で50〜70KB程度まで軽量化して管理するのが最も現実的です。
1. 使うべき公開データとライセンス選定
位置情報アプリの同梱データで最も注意すべき点はライセンスの継承条項（Share-Alike）です。結論として、「国土数値情報（C28）」＋「OurAirports」の2つを主軸にし、OpenStreetMapは直接同梱せず最新施設の照合参考にとどめる構成が最も安全です。
| データソース | 収録内容 | ライセンス・商用配布 | そらメモでの推奨役割 |
|---|---|---|---|
| 国土数値情報（空港データ C28） | 空港の面形状（ポリゴン）・ターミナル・標点位置・定期便の有無（JGD2011） | 商用可・改変自由（出典記載のみ） | ジオフェンスポリゴンの主ベース。日本国内の空港範囲が面データで揃う。 |
| OurAirports (airports.csv / runways.csv) | IATA/ICAOコード・滑走路両端の緯度経度・延長・閉鎖フラグ（GitHubで随時更新） | パブリックドメイン（商用可・改変自由・帰属任意） | 滑走路ベクターラインの主ベース。両端座標が構造化済みで即ベクター化できる。 |
| OpenStreetMap（Overpass API等） | 最新のターミナル・新設滑走路・駐機場まで極めて高精度 | ODbL（派生DBの公開・配布時に継承義務と出典表示あり） | 同梱DBには直接混ぜない。新設施設の位置確認用、または別枠でODbL準拠公開する前提でのみ利用。 |
| 国土交通省 eAIP（AIS JAPAN） | 航空法に基づく公式の最新滑走路座標（WGS84） | 閲覧用（自動取得・再配布向けではない） | 手動パッチの検証用。近年滑走路が新設・変更された主要空港の最終確認に使う。 |
OpenStreetMapを同梱マスターに直接混ぜない理由： OSMから空港ポリゴンや滑走路を抽出してGeoJSONやSQLiteへ加工し、アプリに同梱して配布するとODbL上の「派生データベース（改変データベース）」に該当し、利用者からの求めに応じたデータ提供義務（Share-Alike）が発生します。国土数値情報とOurAirportsだけで組めば、この法務・運用コストを完全に避けられます。
2. ジオフェンスポリゴンの作成・軽量化手順
国土数値情報の生ポリゴンは海岸線や敷地境界が細かく、1空港で数百頂点になることがあります。チェックイン用途では「屋内GPSブレを吸収しつつ、頂点数を極限まで減らす」加工を行います。
 * 対象空港の抽出と座標系統一
   * 国土数値情報（C28）から日本の定期便空港（約97〜100箇所）の面データを抽出し、WGS84（EPSG:4326）へ統一します（※JGD2011とWGS84の差は実用上数cm〜数十cmのためそのまま同等に扱えます）。
 * バッファ拡張（+150m〜300m）で屋内GPSブレを吸収
   * 一時的にメートル単位の投影座標系（例：UTMや平面直角座標系）へ変換し、ポリゴン外周に 150m〜300mのバッファ をかけます。
   * これにより、ターミナルの地下駅直結フロア・送迎デッキ・空港直結ホテル・駐機スポット端でも「圏外弾き」が起きにくくなります。
 * 頂点の簡略化（Ramer-Douglas-Peucker または凸包）
   * バッファ後の外周に対し、Ramer-Douglas-Peucker（RDP）アルゴリズムを許容誤差 30m〜50m で適用します（入り組んだ地形が不要な小規模空港は凸包でも十分です）。
   * 目安は 1空港あたり 8〜20頂点。ここまで削ってもチェックイン判定の体感精度は落ちません。
 * 座標の桁数丸め（小数点以下4〜5桁）
   * 緯度経度を 小数点以下4桁（約11m精度）〜5桁（約1.1m精度） に丸めます。不要な浮動小数点桁を削るだけでJSON容量が40〜50%縮みます。
 * 高速判定用BBox（外接矩形）の事前計算
   * 各空港に [minLng, minLat, maxLng, maxLat] を事前計算して持たせます。アプリ実行時はまずBBoxで99空港を瞬時に除外し、該当候補の1空港だけに点と多角形の内外判定（Ray-Casting法）を走らせることで、バッテリー消費をほぼゼロに抑えます。
 * 容量の目安： 1空港 15頂点 × [lng, lat] ≒ 約300バイト → 100空港で生JSON 約30〜40KB（gzip圧縮後 約12KB）。
3. 印カード用「滑走路ベクターライン」の生成・正規化手順
緯度経度をそのまま描画すると、高緯度（新千歳：北緯42.8°）と低緯度（那覇：北緯26.2°）で経度1度あたりの実距離が異なるため、滑走路の角度と縦横比が歪みます。ビルド時に以下の数式で正規化済みの描画座標に変換しておきます。
 * 有効な滑走路の両端座標を抽出
   * OurAirports の runways.csv から対象空港のICAOコードで絞り込み、closed == 0 かつ舗装済みの滑走路端点 (le_lat, le_lng) と (he_lat, he_lng) を取得します。
 * コサイン補正による局所平面投影（真の方位・比率を復元）
   * 対象空港の全端点の中心 (\phi_0, \lambda_0) を原点とし、各端点を次の平面座標 (x, y) へ変換します（北が上）。
     
   * 羽田（\cos 35.55^\circ \approx 0.814）や新千歳（\cos 42.78^\circ \approx 0.734）の横縮みを正しく補正でき、実際の空港と同じ美しい交差角になります。
 * 正方形キャンバス [0.0, 1.0] への正規化（マージン付き）
   * 全端点の幅 W = x_{\max} - x_{\min}、高さ H = y_{\max} - y_{\min} から最大辺 S = \max(W, H) を求めます。
   * 「印」カード内で余白を美しく取るため、描画領域を 0.15 〜 0.85（有効幅 0.70）に設定し、中央揃えでスケーリングします。
     
   * ※SVG/Canvasは下方向がY正のため、v の符号を反転しておくとアプリ側の描画コードが座標変換ゼロで済みます。
 * 小数点以下3桁へ丸めて配列化
   * 1本の滑走路を [u1, v1, u2, v2] の4数値（例：[0.241, 0.782, 0.618, 0.214]）に圧縮します。
   * 滑走路が1本だけの地方空港でも、そのまま描画するとカードの幅いっぱいに伸びて見栄えが統一されます（長さを空港規模で変えず、角度と本数の個性だけを見せるのがモダンな印にするコツです）。
 * 容量の目安： 1空港 1〜4本 ≒ 約50〜120バイト → 100空港で生JSON 約8〜10KB。
4. ジオフェンス軽量化＆滑走路正規化の挙動を確認する
下のツールで空港やパラメータを動かすと、「バッファ拡張＋RDP簡略化で頂点数と100空港の合計容量がどう変わるか」と「コサイン補正の有無で印カードの滑走路角度がどれだけ歪むか」を視覚的に検証できます。
5. 破綻しないデータ管理・更新パイプライン
約100空港のデータは一度作ったら終わりではなく、滑走路の新設（例：福岡第2滑走路など）・閉鎖、新ターミナル開業、空港名称変更が年に数回発生します。生データを手作業で直接編集すると次回更新時に上書き事故が起きるため、以下の4層構造（Git管理）にします。
airport-master/
├── raw/                     # ① 公開データのスナップショット（手編集禁止）
│   ├── mlit_c28_airports.geojson
│   └── ourairports_runways.csv
├── overrides/               # ② 手動パッチ層（ここだけ人間がメンテナンス）
│   ├── airport_overrides.json   # 新設滑走路・閉鎖除外・ポリゴン微修正・和名統一
│   └── test_points.json         # 各空港ターミナルの実測テスト座標（CI用）
├── scripts/
│   └── build_master.py      # ③ 抽出→バッファ→RDP→コサイン正規化→検証→出力
└── dist/
    ├── airports_master.json # ④ アプリ同梱ファイル（master_version付き）
    └── preview_100.html     # 目視確認用（全100空港の地図＋印カード一覧）

ビルド時に必ず通す4つの自動テスト（CIバリデーション）
スクリプト実行の最後に次のチェックを入れ、1件でも落ちたらリリース用JSONを出力しない仕組みにします。
 * 代表地点IN判定テスト： 各空港のターミナル中央・展望デッキ・搭乗口付近の既知座標（test_points.json）が、生成後のジオフェンスポリゴン内で必ず true になるか検証。
 * 隣接空港の干渉チェック： 距離が近い空港ペア（例：羽田と調布・横田、伊丹と神戸・関西、福岡と佐賀など）のバッファ後ポリゴン同士が重なっていないか交差判定。
 * 滑走路ベクター健全性チェック： すべての定期便空港に最低1本以上の滑走路ラインがあり、全座標が 0.10 〜 0.90 の安全領域内に収まっているか検証。
 * 全100空港の目視プレビュー生成： ビルドの副産物として、全空港のジオフェンス地図と印カード画像を1ページに並べた preview_100.html を自動出力。リリース前に人間がスクロールして5分で異常（滑走路が極端に短い、離島が切れている等）を最終確認します。
アプリ側の更新戦略（同梱＋軽量ハイブリッド配信）
 * 基本はアプリバイナリ同梱： Phase 1は dist/airports_master.json（約50KB）をアプリに組み込み、インストール直後から完全オフライン動作させます。
 * 緊急時だけリモート差分更新（任意）： アプリ起動時にサーバーの極小ファイル master_manifest.json（{"version": 202611, "sha256": "...", "url": "..."}）だけを非同期確認し、同梱版より新しければ50KBのJSONを端末ローカルへ上書きキャッシュします。これにより、滑走路変更やGPS判定トラブルが起きてもストア審査を待たずに当日修正できます。
