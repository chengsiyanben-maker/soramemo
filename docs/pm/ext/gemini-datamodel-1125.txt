Phase 1（MVP）では、「オフラインでもアプリが完全に動く（ローカルファースト）」ことと、「Phase 2〜3の特別塗装機・修行モードを後から足してもテーブル構造を壊さない」ことの2点を軸にデータモデルを設計します。
1. 設計の大原則（3つの前提）
 * ローカルDBを「唯一の正（Single Source of Truth）」にする
   画面（地図・図鑑・フライト履歴）は常に端末内DB（SQLite や IndexedDB）だけを参照して描画します。サーバー同期は裏側の非同期処理に完全に切り離すことで、機内モードでも遅延ゼロで動作します。
 * すべてのIDはクライアント側で ULID を発行する
   サーバー採番の連番IDにすると、オフライン中に作成した記録にIDを振れず、再送時の重複やリレーション崩れが起きます。時系列ソート可能な ULID（またはUUIDv7）を端末で生成し、そのままサーバー同期時の冪等キーとして使います。
 * ゲストIDで即開始し、後からアカウントへ昇格できる構造にする
   初回起動時に端末固有の local_user_id を自動生成してローカル保存します。初回チェックイン後などに任意でクラウドバックアップをONにした際、クラウド側の account_id にデータを安全にマージします。
2. Phase 1（MVP）の主要データモデル（4テーブル）
① 空港マスタ（airports：アプリ同梱・読取専用）
日本の空港データは約100件と非常に軽量なため、アプリ本体にJSON/SQLiteとして同梱します。これで完全オフラインでも位置判定・距離計算・印の描画が完結します。
| カラム名 | 型 | 用途・設計意図 |
|---|---|---|
| code | string (PK) | IATA 3レターコード（HND, ITM 等）。印カードの表示主役。 |
| icao | string | ICAOコード（RJTT 等）。外部航空データ連携時の照合用。 |
| name_ja / name_en | string | 羽田空港 / Tokyo Haneda。 |
| region_code | string | kanto, kyushu_okinawa 等。図鑑の「地方別小目標」の集計キー。 |
| category | enum | scheduled（定期便空港） / airfield（飛行場）。Phase 1は scheduled のみ表示し、Phase 3の飛行場追加に備えて列だけ先行確保。 |
| center_lat, center_lng | number | 地図ピン表示および通常時の最寄り空港距離計算用。 |
| geofence_json | json | ターミナル全体＋滑走路を含む簡易ポリゴン座標配列（判定円より誤判定が少なく、屋内ブレに強い）。 |
| runway_lines_json | json | 「印」カード描画用の正規化ベクター座標（各滑走路の始点・終点）。空港ごとに画像ファイルを持たず軽量に描画するため。 |
| master_version | int | 空港の新設・滑走路変更時にアプリ更新または差分取得するバージョン。 |
② チェックイン・訪問ログ（checkin_logs）＋ 集計キャッシュ
「現地の印」と「オンボーディングで選んだ訪問済みメモ」を同じテーブルで管理し、履歴は追記型（Append-only）にします。図鑑一覧を高速に描くため、空港ごとの最新状態（訪問回数・初回現地日・メモか印か）はローカルでビューまたはキャッシュテーブルとして集計します。
| カラム名 | 型 | 用途・設計意図 |
|---|---|---|
| id | ulid (PK) | クライアント生成ID。サーバー送信時の重複防止キーになる。 |
| airport_code | string (FK) | airports.code を参照。 |
| kind | enum | onsite_stamp（現地GPSチェックインの印） / past_memo（自宅等で登録した訪問済みメモ）。 |
| checked_in_at | timestamp | チェックイン実行時の端末時刻（ISO8601＋タイムゾーン）。 |
| local_date | string | YYYY-MM-DD（JST基準）。同日同空港の重複チェックインを防ぐ一意判定キー。 |
| capture_method | enum | gps_exact（通常オンライン） / gps_rescue_cache（屋内ズレ救済） / offline_reserved（機内モード・圏外予約保存）。 |
| captured_lat, captured_lng, accuracy_m | number? | 判定時の参考メタデータ。プライバシー保護のためSNSシェア画像には一切出力しない。 |
| sync_status | enum | pending（送信待ち） / syncing / synced（確定） / manual_error。画面上の「送信待ち」ピル表示に直結。 |
| deleted_at | timestamp? | 訪問済みメモの取り消し用（物理削除せず論理削除にして同期復活を防ぐ）。 |
③ フライト記録＆予定（flight_records）
「次のフライト予定」と「乗った後の確定記録」を同じテーブルの status 違いで管理します。これにより、ホームで入れた予定が搭乗後に1タップでそのまま確定履歴へ昇格し、二度入力がなくなります。
| カラム名 | 型 | 用途・設計意図 |
|---|---|---|
| id | ulid (PK) | クライアント生成ID。 |
| status | enum | planned（予定・ホームのカウントダウン対象） / completed（確定履歴・空の上の時間集計対象） / simulated（Phase 3の修行試算便用に予約）。 |
| flight_date | string | YYYY-MM-DD。月別グループ表示とソートキー。 |
| dep_airport_code, arr_airport_code | string (FK) | 発着空港コード。ルート地図の弧線と大圏距離計算に使用。 |
| carrier_code | string? | JL, NH, BC 等。航空会社ロゴの代わりに2レター識別ピルの色決定に使う。予定段階では未入力（null）許容。 |
| flight_number | string? | 便名数字（519 等）。予定段階では未入力許容。 |
| aircraft_type | string? | A359, B788 等（Phase 2の便名補完・手動入力用）。 |
| dep_time_scheduled, arr_time_scheduled | string? | HH:mm（予定時刻）。 |
| duration_min | int | 飛行時間（分）。「空の上の時間」の合算元。時刻未入力時は空港間距離からの標準推計値を仮セットし、後から上書き可能にする。 |
| distance_km | int | 発着空港の座標から自動算出して保存する飛行距離。 |
| linked_checkin_id | ulid? | どのチェックイン完了カードから登録したかの紐づけ。 |
| loyalty_ext_json | json? | Phase 3「修行」モード用の予約拡張枠（プログラム種別・運賃積算率・自動計算ポイント・ユーザー手動上書き値）。Phase 1では常に null で置いておけば、後のマイグレーションが不要。 |
| sync_status, updated_at, deleted_at | 各種 | オフライン同期・競合解決（LWW）・論理削除用。 |
④ 予約保存・オフライン同期キュー（sync_queue）
チェックイン予約保存だけでなく、オフライン中のフライト記録や設定変更もすべて1つのOutbox（送信箱）キューに積みます。羽田と新千歳で連続して機内モード操作しても、時系列を保って確実に同期できます。
| カラム名 | 型 | 用途・設計意図 |
|---|---|---|
| queue_id | ulid (PK) | 作成順がそのまま送信順（FIFO）になる。 |
| idempotency_key | string (UNIQUE) | 例：checkin:{ulid}:upsert。再送してもサーバー側で二重登録されない保証。 |
| entity_type | enum | checkin_log / flight_record / user_setting。 |
| entity_id | ulid | 対象レコードのPK。同期完了時に元テーブルの sync_status を synced へ書き戻すために使う。 |
| operation | enum | upsert / delete。 |
| payload_json | json | 送信する時点のスナップショット。 |
| state | enum | pending（待機） / syncing（送信中） / retry_wait（再試行待ち） / synced（完了） / manual_error（手動対応要）。 |
| retry_count | int | 失敗回数。指数バックオフ間隔の算出に使う。 |
| next_retry_at | timestamp? | 次回自動リトライを許可する時刻。 |
| last_error_code | string? | デバッグ・ユーザー案内用の直近エラー種別（タイムアウト／時計ズレ等）。 |
3. オフライン同期の設計ポイント（壊れないための5つの鉄則）
① 3.5秒タイムアウト＋冪等性による「パケ詰まり吸収」
空港で最も厄介なのは完全圏外ではなく、「サーバー側では登録が成功したのに、電波詰まりで端末への応答が返らずタイムアウトする」ケースです。
 * 端末側は3.5秒で通信を打ち切り、ユーザーには即座に「予約保存（送信待ち）」の完了カードを出して操作を解放します。
 * 後から再送した際、サーバーは idempotency_key を照合し、すでに登録済みならエラーにせず 200 OK（同期済み） を返します。これにより二重チェックインもエラー停止も起きません。
② 送信順序（FIFO）と指数バックオフ
乗り継ぎ時に「羽田で予約保存 → 搭乗便を記録 → 新千歳で予約保存」と続いた場合、queue_id（ULID）の昇順で順番に送信します。
 * 一時エラー（圏外・タイムアウト・5xx）： retry_wait へ移し、5秒 → 30秒 → 2分 → 10分の指数バックオフで再試行します。
 * 恒久エラー（端末時計の1時間以上のズレ・認証切れ・4xx）： 無限リトライすると電池を消耗するため即 manual_error へ落とし、ホームやマイページに控えめな案内を出します。
③ 競合解決（Conflict Resolution）の明確なルール
複数端末でのログインや、ゲスト状態からのクラウドバックアップ統合時にデータがぶつかった場合、エンティティごとにルールを固定します。
 * チェックイン印（checkin_logs）：
   * 同日重複の吸収： (account_id, airport_code, local_date, kind='onsite_stamp') に複合一意制約を設け、同日の重複は早い時刻の記録を正として自動マージします。
   * 昇格優先の原則： 同じ空港に past_memo（訪問済みメモ）と onsite_stamp（現地の印）が両方ある場合、図鑑の表示は常に onsite_stamp を上位として扱います。
 * フライト記録（flight_records）：
   * レコード単位の LWW（Last-Write-Wins：updated_at が新しい方を採用） とします。物理削除せず deleted_at を使うことで、オフライン端末が古いレコードを復活させる事故を防ぎます。
④ バッテリーを守る「イベント駆動」の同期トリガー
バックグラウンドで常時通信チェックを走らせると、空港で最も嫌われる「電池を食うアプリ」になります。同期ワーカーの起動は次の4トリガーだけに絞ります。
 * チェックイン・記録の保存直後（オンラインかつ上限3.5秒）
 * OSのネットワーク状態が「オフライン → オンライン」に変わった瞬間
 * アプリがバックグラウンドからフォアグラウンドへ復帰した瞬間
 * ユーザーがホームの「送信待ち」ピルを手動タップしたとき
⑤ ゲスト利用 → クラウドバックアップの安全な昇格手順
ログイン時にローカルデータを消してサーバーで上書きすると、オンボーディングや初フライトの記録が吹き飛びます。
 * アカウント認証完了後、まず端末内の未同期キューと全ローカルレコードをサーバーへアップロード（マージ）します。
 * サーバー側で重複吸収・マージを終えた最新スナップショットを端末へ差分ダウンロードし、local_user_id を account_id に紐づけて昇格を完了します。
4. オフライン同期キューのライフサイクル検証
チェックインやフライト記録がローカルDBに保存されてからサーバーへ確定するまでの流れと、通信トラブル時の振る舞いを下の図でシナリオ別に追えます。
この4テーブル＋Outbox同期キューの設計にしておけば、Phase 1では最小構成でオフライン耐性を100%担保しつつ、Phase 2の特別塗装機テーブル追加やPhase 3の loyalty_ext_json を使った修行計算を、既存ユーザーのデータを傷つけずにそのまま積み上げられます。
