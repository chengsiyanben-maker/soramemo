ブランチ checkin/ios-plan・下書きのプルリクエスト。PM の指示 11/17 20時30分・11/18 0時15分、決定事項【11/17】（iPhone のアプリにする・まず計画・自宅の Mac で作る）。

## 1. 作り方の比べ

| | A 今の web を包む（Capacitor） | B 一部をネイティブ（Capacitor＋自作のプラグイン） | C PWA のまま（ホーム画面に追加） | D 全部ネイティブ（Swift） |
|---|---|---|---|---|
| 中身 | src/index.html をアプリの中に入れ、WKWebView で出す。位置・通知・カメラ・共有は Capacitor の部品 | A に加え、チェックインの位置の判定・通知・ウィジェットなどだけ Swift | 今のまま。Safari の「ホーム画面に追加」 | 画面をすべて作り直す |
| 手間 | 小（2〜4週間。変える所は下の2） | 中（A のあとで少しずつ） | なし | 大（数か月。1人では重い） |
| 審査 | 4.2（ウェブを包んだだけ）に当たらないよう、ネイティブの部品を使う（下の3） | 通りやすい | 審査なし（ストアに出ない） | 通りやすい |
| 危なさ | 1つの index.html を web と iPhone で共有できる。WKWebView の違い（サービスワーカーが使えない等）に注意 | Swift の部分は1人で持ち続ける | ストアで見つけてもらえない。1月のストア公開に合わない | web と二重に持つことになる |

**おすすめ：A で始め、必要なところだけ B に寄せる。** 理由：1人開発で、今の画面（ホーム・図鑑・運用・修行・経営）をそのまま使える。web と同じ src/index.html を組み立てて入れるので、直しが両方に効く。Capacitor 8（2025年12月）が今の版。

- やらないこと：アプリの中で https://soramemo.jp を読み込むだけの形（server.url）。審査で「ウェブを包んだだけ」とされやすく、電波がないと何も出ない。組み立てた web/ のファイルをアプリの中に入れる

## 2. 変える所の一覧（コードは次の段で）

| 所 | 今 | iPhone のアプリで | 担当 |
|---|---|---|---|
| 位置情報 | navigator.geolocation（getCurrentPosition・watchPosition の5か所） | @capacitor/geolocation に切り替える薄い入れ物を1つ作り、5か所はそれを呼ぶ。使うのは「使用中のみ」（バックグラウンドは使わない）。Info.plist に使う理由の文 | チェックイン |
| プッシュ通知 | Web Push（sw.js・VAPID・push-subscribe） | @capacitor/push-notifications で APNs の端末トークンを取り、サーバーに送る。送る側（flight-watch など）は APNs にも送る形が要る（.p8 の鍵は Supabase の秘密の値に入れる。コードに書かない）。web の人は今の Web Push のまま | チェックイン（受け取り）・データ（表と送る側） |
| ログイン | メールの6けたのコード（signInWithOtp・verifyOtp）＋ Cloudflare Turnstile | コードの入力はそのまま動く。Turnstile はアプリの中の住所（capacitor://localhost）を許可に足すか、アプリでは使わない（アプリの中ではロボット除けを別の形に）。どちらにするか本人に | チェックイン・データ |
| 退会 | delete-account（あり） | アプリの中から退会できることが審査の決まり（5.1.1(v)）。今の形で足りる | — |
| 地図 | Leaflet・MapLibre を jsdelivr から読む | アプリの中に入れる（電波が弱い空港でも出るように）。CSP の script-src を合わせる | チェックイン |
| バーコード（搭乗券） | BarcodeDetector がなければ zxing | iPhone の Safari には BarcodeDetector がないので今も zxing。アプリでは Capacitor のバーコードの部品（ネイティブのカメラ）にすると速く、審査でも「アプリらしさ」になる。カメラの使う理由の文 | チェックイン |
| マイク（管制の聞き取り） | getUserMedia（音声） | マイクの使う理由の文。約80MB の音声認識は、アプリでは初回に読む形のまま | チェックイン |
| オフライン | サービスワーカー（sw.js） | WKWebView の中ではサービスワーカーが動かない。アプリには最初から全部入っているので、画面は電波なしで開く。データの読み込みの失敗は「もう一度」の画面にする | チェックイン |
| 共有 | navigator.share（3か所） | @capacitor/share（ネイティブの共有シート） | チェックイン |
| 有料（そらメモ＋） | Stripe の申し込み画面 | 下の3の「有料」を見て決める。最初の版はアプリの中に申し込みの入口を出さない案 | 本人の判断 |
| 3D（空港の3D・PR #123） | three.js を jsdelivr から | アプリの中に入れる | チェックイン |
| 外部のリンク | target=_blank | アプリの中のブラウザ（@capacitor/browser）で開く | チェックイン |

画面が変わる所（アプリだけの最初の案内・位置と通知の許可を頼む前の説明の1枚・オフラインの画面）は、作る前にデザイン担当の画面案を待つ。

## 3. App Store の審査で引っかかりそうな所

- **4.2 最低限の機能（ウェブを包んだだけ）**：ウェブを包み直しただけのアプリは断られる。そらメモは位置でのチェックイン・通知・カメラ（搭乗券）・ネイティブの共有・下のタブ帯（今もある）があり、ネイティブの部品で動かせば当たりにくい。ウェブのヘッダー・「ホーム画面に追加」の案内・ブラウザ向けの文はアプリでは隠す
- **位置情報の理由の書き方（5.1.1・Info.plist）**：「使用中のみ」にし、理由は具体的に書く。案：「空港にいるかを確かめて、チェックインの印を押すために使います。いる場所は印を押すときだけ送り、ほかの人には見せません」。バックグラウンドの位置は使わない（使うと審査が重くなる）。許可を頼む前にアプリの中で1枚の説明を出す
- **カメラ・マイク**：「搭乗券のバーコードを読んで乗った便を記録するために使います」「管制の音声を文字にするために使います（音声はこの iPhone の中だけで処理します）」の形で書く（実際の処理に合わせて確かめる）
- **非公式アプリの書き方・航空会社の名前（5.2 知的財産）**：説明文とアプリの中に「非公式アプリです。各航空会社・空港とは関係ありません」。アイコン・スクリーンショットに会社のロゴを出さない（決定事項どおり）。会社名は事実の記録としてだけ
- **データの出典**：ODPT（公共交通オープンデータ）・adsb.lol（ODbL）・FAA・気象通報・国土交通省「空港一覧」。アプリの中の出典の画面は今のまま。ODPT の利用規約でアプリでの配信が許されるか、データ担当の確認表（そらメモ_外部データの利用規約の確認表）をもう一度見る
- **有料（3.1.1）**：アプリの中でデジタルの機能（そらメモ＋）を売るなら、原則は Apple のアプリ内課金。日本では2025年12月18日からスマホ新法（MSCA）で、アプリの中でほかの決済や外の購入ページへのリンクも使えるようになった（手数料はかかる。条件は申請の前に Apple の日本向けの案内で確かめる）。おすすめ：最初の版はアプリの中に申し込みの入口を出さず、ウェブで入った人の特典はそのまま使えるかを申請の前に確かめる。課金を稼ぎやランキングに効かせない決まりは同じ
- **プライバシー**：App Store の「プライバシーの表示」（集めるデータ：メール・位置・使い方）を出す。プライバシーポリシーの URL（今の privacy.html）
- **アカウント**：メールのコードだけのログインなので「Apple でサインイン」は必須ではない（ほかの会社のログインを使っていないため）
- **デモで試す**：審査の人がログインせずに中身を見られるので、そのまま残す。審査用のアカウントも用意する（申請の画面に書く）
- **位置で押す仕組み**：審査の人は空港にいない。審査メモに「デモで試す」と、印の押し方の説明を書く

- 本人に決めてほしいこと：個人で出して本名を出すか／法人を作ってから組織で出すか（D-U-N-S の取得に数週間かかることがある）

## 5. 通知の作り直し

- 今：Web Push（VAPID の鍵・push-subscribe で購読を保存・flight-watch などが送る。同じ便は tag と renotify で上書き）
- アプリ：APNs。端末トークンを push-subscribe に「種類 = apns」として送り、送る側は種類で Web Push と APNs を分ける。上書きは APNs の apns-collapse-id（今の tag と同じ値）でできる
- 要るもの（データ担当へ依頼する予定）：購読の表に種類の列（移行と RLS をセット）・APNs に送る関数（.p8 の鍵・Key ID・Team ID は Supabase の秘密の値。コードに書かない）
- 決定事項【11/13】の通知のまとめ方（1便1通知・15分から・門限の10分前）は変えない

## 6. 本人が Mac でする手順（ターミナルに1行ずつ貼る）

作業場所は ~/dev/soramemo（Mac には Homebrew・git・gh・node・Xcode がある）。今はまだ準備と確かめだけで、アプリのコードは次の段（計画が決まってから）で作る。

まず Xcode が使えるか確かめる
```
xcode-select -p
```
```
sudo xcodebuild -license accept
```
```
xcodebuild -version
```
（Xcode 26 より古ければ App Store から更新する）
iPhone のシミュレーターがあるか確かめる
```
xcrun simctl list devices available | grep iPhone | head -5
```
Capacitor 8 は Node 22 以上・Xcode 26 以上が要る（iOS 15 以上で動く）。CocoaPods は要らない（新しく作るときは Swift Package Manager）。node の版を確かめる（v22 以上）
```
node -v
```
（v22 より古ければ）
```
brew install node@22 && brew link --overwrite --force node@22
```
リポジトリを最新にする
```
cd ~/dev/soramemo
```
```
git fetch origin && git status -sb
```
（次の段でチェックイン担当が作るブランチ checkin/ios-app ができたら）
```
git switch checkin/ios-app
```
```
npm ci --prefix tools && node tools/build.mjs
```
```
npx cap sync ios
```
```
npx cap open ios
```
Xcode が開いたら、上の「Signing & Capabilities」で自分の Apple ID のチームを選び、つないだ iPhone を選んで ▶（Xcode の画面の操作）。

GitHub の二段階認証（12月12日まで）を先に済ませる（決定事項【11/17】）。

## 7. 順番の案

1. 本人：登録の形（個人か組織か）・有料の扱い・Turnstile をアプリでどうするかを決める
2. デザイン担当：アプリだけの画面（位置と通知の許可の前の説明・オフラインの画面・アプリでは隠すもの）の画面案
3. データ担当：通知の表に種類の列・APNs に送る関数（移行と RLS をセット）・ODPT の規約の確かめ直し
4. チェックイン担当：checkin/ios-app で Capacitor 8 の土台（ios/ のフォルダ・位置・共有・ブラウザ・カメラの入れ物）。web と同じ src/index.html を組み立てて入れる。下の担当（修行・撮る人用・運用予想）のコードはそのまま動く形
5. 本人：Mac でシミュレーターと自分の iPhone で動かす（無料）→ 年会費を払って TestFlight → 審査に出す（1月のストア公開に合わせるなら、12月中旬に TestFlight）
