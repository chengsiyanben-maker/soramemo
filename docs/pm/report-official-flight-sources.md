# アメリカ・ヨーロッパの公式の便の情報の元（データ担当の報告）

PM の指示（11/16 11時55分）と本人の問い「アメリカとか、ヨーロッパの公式の情報サイトないの？」への答え。空港の止まり具合ではなく、**便ごと（定刻・変更時刻・状態）の公式の元**を、規約の原文（11/16 に読んだ）で確かめた。**コードは作っていない。表も移行も足していない。**

## 1. 結論（先に）
- **すぐ使える形で「一般の無料アプリに出してよい」とはっきり書いた公式の元は、今回見た中にはなかった。** どれも「登録して鍵をもらう」形で、本番で使うには本人のアカウントと、多くは会社との契約（有料のことが多い）が要る
- 条件がいちばん合いそうなのは **FAA SWIM（SCDS）**：無料・登録制・「運航に使わないアプリやサイト」は使ってよいと原文にある。アメリカの空を飛ぶ便（日本発着のアメリカ便を含む見込み）の計画と到着の見込み。ただし、データの流れ（JMS の購読）を受け続ける仕組みが要り、Supabase の毎分の処理だけでは受けにくい（重い）
- **ルフトハンザ**は無料の公開の枠があり、便の状態を便名で引ける。ただし規約に「ほかのデータと合わせない（combine, associate, synthesize）」「ほかへ渡さない」があり、私たちの「全機の航跡と合わせて出す」使い方とぶつかるおそれがある。商用（広告つき・課金つき）は書面の許可が要る
- **スキポール**は無料の枠があるが「実際の旅客を助ける用途だけ」「保存は24時間まで」。記録を残す（消さない）私たちの作りとは合わない。画面に一時的に出すだけならあり得る。商用は有料
- **ブリティッシュ・エアウェイズ（IAG）**は試用の契約だけで、**商用は別の契約が済むまで不可**。便の情報の API は版の終わりが「2015年12月」と書かれたまま
- **エールフランス‐KLM**は開発者の頁が画面の中で読み込む作りで、今回は規約の原文を読めなかった（本人が登録したときに読む）
- **フランクフルト空港**には公開の便の API が見つからなかった。サイトの規約は「ブラウザーで見るだけ」「載せる・作り変えるには書面の同意」で、**サイトから便の表を取ってくることはできない**

## 3. 私たちの作りとの合い方
- 今の PR #104（foreign_legs）は、全機の記録（adsb.lol、ODbL）から海外の会社の便の実績を取り出していて、**外への問い合わせは増やしていない**。公式の元はその「答え合わせ」か「定刻の元」として足す位置づけになる
- 「航路と機体の記録は消さない」との相性：スキポール（24時間まで）・ルフトハンザ（終わったら使うのをやめる・合わせて別の表を作るのも対象）は、**公式の元の値を長く残せない**。残すのは私たちの観測（adsb.lol）だけにし、公式の値は画面に出す間だけ持つ形になる
- 「ほかのデータと合わせない」（ルフトハンザ）は、乗る便の通知（私たちの推定と公式の時刻を1つにまとめる、11/13 の決定）とぶつかる。使うなら、公式の時刻は別の行に「ルフトハンザの発表」と分けて出す形にして、合わせて新しい値を作らない
- FAA SWIM は条件は合うが、受ける仕組み（常に開いた購読）が Supabase の Edge Functions に向かない。小さな常時動くサーバー（有料のことが多い）が要る。広告で「有料の道具は使わない」と決めているが、これは広告の決まりなので、データの受け口に費用をかけてよいかは本人の判断

## 4. 本人に決めてほしいこと
1. **どれかを試すか**：おすすめの順は ①FAA SWIM（無料・条件が合う。受ける仕組みに手間と費用）②ルフトハンザ（無料の枠。合わせない・保存しない形で、乗る便に LH を選んだ人の画面に「ルフトハンザの発表」を1行）③スキポール（KLM などアムステルダム発着だけ。24時間で捨てる）。BA・フランクフルトは使えない
2. 試すなら、**アカウントを作るのは本人（旅そら ryoairtrip@gmail.com）**。鍵は Supabase の秘密の設定に本人が入れる（コードに書かない）。登録のとき、エールフランス‐KLM とスキポールの一般条件の原文を貼ってもらえれば、表の「未確認」を埋める
3. 広告つき・課金つきのアプリが「商用」に当たるか、ルフトハンザとスキポールに問い合わせるか（問い合わせ文はデータ担当が書く。差出人は旅そら）
4. 決まるまでは、今の PR #104（自分の観測から集める）で進める
