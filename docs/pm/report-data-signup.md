## 作ったもの
- `supabase/migrations/20261104000146_user_profiles.sql`：利用者のプロフィールの表 `user_profiles`（移行と RLS をセット）
  - 似た表はなかった（`user_data_prefs` はデータの使い方の設定、`shugyo_prefs` は修行の設定）ので新しく作った。1人1行
  - 列：表示名（1〜20文字・空でも可）、登録日、同意した規約の版・プライバシーポリシーの版（改定日 YYYY-MM-DD）と同意した日時、使い方の答え（`spot` 撮る・`shugyo` 修行・`casual` 気軽・`unanswered` 未回答。アプリの PERSONAS のキーと同じ）と答えた日時
  - アカウントができたときに自動で1行作る（auth.users の追加をきっかけに）。いまいる利用者の分も作る（登録日は auth.users の作成日、同意は空）
  - RLS：本人の行だけ読める。本人が直せるのは表示名と使い方の答えだけ（列ごとの権限）。行を作る・消すのはサーバーだけ
  - 登録日・答えた日時・同意した日時はサーバーの時刻で入る。答えた日時は答えが変わったときだけ入れ直し、未回答に戻すと空
  - 同意は関数 `agree_terms(規約の版, プライバシーポリシーの版)` で記録する
  - アカウント削除（auth.users の削除）で一緒に消える
- `tests/sql/t85_user_profiles.mjs`：上の動きを確かめるテスト（19項目すべて通過。既存の SQL のテストも通過、番号の重なりなし）
- 影響：**チェックイン・経営のどちらの表・関数・画面も変えていない**。いまのアプリはこの表を読まない（使い方の答えはまだ端末の localStorage）。つなぐのは画面の担当の仕事

## 2. アカウント削除で消すもの・残すもの（結論）
いまの削除（`delete-account` → Stripe の定期支払いを止める → auth.users を消す）で、利用者に結びつく表はすべて `on delete cascade` で消える。新しい `user_profiles` も同じ。

| 区分 | 中身 | 削除のとき |
|---|---|---|
| 本人の記録 | チェックイン・乗った便（flights・記録帳・国際線）・修行の設定・データの使い方・プロフィール・イベントのボーナス・管制の協力者の登録・経営の会社と機体・路線・ランキングの毎日の記録・友だち など | **消す**（今のまま） |
| 全機の記録（だれのものでもない） | 便の実績・便の航跡・空港ごとの全機の航跡・機体の便（reg_legs）・滑走路の学習・ゴーアラウンド・運用・特別塗装機を見た記録・空の道すじ・天気。ファイル置き場（cold）に移すのもこれだけ | **残す**（利用者IDを持たないので削除の影響を受けない） |
| 個人の分からない記録 | 使われ方・エラー（起動ごとの番号だけ、180日で消す）・断られたチェックイン | 残す |

- 「航路と機体の記録は消さずに残す」は**全機の記録のこと**で、利用者IDを持たない表なので、削除と両立している。本人が乗った便（flights）は個人の記録なので消すのが筋（ここを残すと、退会した人の移動の記録が残ってしまう）
- 注意点（データベースの外・他の人への影響）
  1. 通知の宛先（push_subs）は利用者に結びついていないので、削除しても残る（通知が失敗したら消える）。削除の画面で端末の通知の登録も外すのがよい
  2. 手元のパソコンのバックアップには、削除した人の記録が残る
  3. Stripe には顧客の記録が残る（定期支払いは止まる）
  4. 経営で他の人に響くもの：アライアンスのリーダーが消えるとアライアンスごと消える／出資の相手が消えると出資の記録が消える／コードシェアの相手が消えると契約が消える（経営の担当で扱いを決める。今回は触っていない）

## 3. 確認コードのメールの送信上限（結論）
- Supabase の標準のメール：**1時間に2通**（プロジェクト全体）。告知には使えない
- 自前の SMTP（計画書では Gmail）にすると、Supabase 側の上限はダッシュボードで変えられる（Authentication → Rate limits）。本番の値は見られていないので確かめてほしい
- そのほかの上限：同じ人のコードの送り直しは60秒に1回、同じ IP からの登録・ログインは5分に30回
- Gmail の無料のアカウント：**1日およそ500通**（Google Workspace はおよそ2,000通）。超えると最大24時間ほど送れなくなり、**今いる人もログインできなくなる**
- 見積もり（1人の登録で送り直しを含め約1.3通。投稿の後の最初の1時間に4割が集中すると仮定）

| 1日の登録 | 最初の1時間のメール | 1日のメール | Gmail 500通/日 | Supabase の上限が 30通/時なら |
|---|---|---|---|---|
| 50人 | 約26通 | 約65通 | 足りる | ぎりぎり |
| 100人 | 約52通 | 約130通 | 足りる | 足りない |
| 300人 | 約156通 | 約390通 | ぎりぎり（ふだんのログインと合わせると超えうる） | 足りない |
| 1,000人 | 約520通 | 約1,300通 | 足りない | 足りない |

- 結論：計画どおり「1日およそ100人ずつ」なら Gmail で足りる。ただし Instagram の投稿は一度にあふれうるので、①Supabase の上限を Gmail を超えない値（例：1時間100通・1日で500通に届かない程度）にする、②登録の入口を TestFlight／クローズドテストの人数で絞る、③大きく告知するなら送信専用のメールサービスに切り替える、のどれかが要る

## 本人に決めてほしいこと
1. 表示名をほかの人に見せるか（ランキング・友だちなど）、同じ名前を許すか。経営の会社名とは別にしている
2. 同意の記録は最新の1回だけ（上書き）。改定のたびの履歴を残すか、改定のときに同意し直してもらうか
3. いまいる利用者は同意が空のまま。次に開いたときに同意を求めるか
4. 本番への反映（「反映して」で流す）。流す前に `node tools/migrations.mjs rebase` で番号を付け直す
5. メールの送り方：Gmail のままにするか、送信専用のサービスにするか。Supabase の送信の上限を何通にするか
6. 削除のときの通知の登録の解除、バックアップを何日残すか（プライバシーポリシーに書くか）、バックアップの関数（admin_backup）に新しい表を足すか
7. 経営で他の人に響く削除（アライアンス・出資・コードシェア）の扱い（経営の担当へ）
