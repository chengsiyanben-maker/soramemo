# 報告：海外の航空会社の便のデータを自分で集める（データ担当・11/16）

PM の指示（11/16 11時40分、本人「海外のデータも収集したい」）。report-foreign-carriers（PR #101）の続き。
ブランチ data/foreign-collect（main 2ae2e1f から）。下書き PR。本番には入れていない。

## 結論（先に）
- **海外の会社の便は、すでに毎日の全機の記録に入っていた。** reg_legs（機体ごとの便）と airport_tracks_all（空港ごとの上昇・降下の航跡）は、呼び出し符号が「英字3文字＋数字」の機体なら会社を問わず残している。足りなかったのは「1便1回の実績」としての取り出しと、いつもの時刻
- そこで、**外への問い合わせを1回も増やさずに**（adsb.lol・adsb.im とも0回）、毎日の記録から海外の会社の便の実績を取り出して残す表と、「いつもの時刻」と、その日のずれ（推定）を返す関数を作った（移行 171・テスト t110）
- 乗る便に選んだ海外の便の見張り（案A：門限ギリギリ・ダイバート・引き返し）は、この記録の上に作る次の仕事。通知の決まりと表の持ち方を決めてもらう必要があるので、今回は作っていない（下の 5）

## 3. 確かめた結果

- 速さ（手元の PGlite）：航跡21万6千行（30空港×60日）のうち1日2,400回を作るのに約0.2秒。空港と日の主キーで引くので、表が大きくなってもその日の分だけ読む

## 4. 規約と回数
- **adsb.lol**：問い合わせは増えない（今の記録を使うだけ）。データのライセンスは ODbL 1.0（「use it freely, just keep it open」、adsb.lol の Historical data の頁）。API の回数の上限は「環境の負荷で変わる」「4xx が返るなら使い方が間違っている」「将来は受信機を出している人に API キー」（adsblol/api の README）。ODbL なので、foreign_late の答えと画面には出典「adsb.lol（ODbL）」を必ず添える（関数の note に入れた）。作った表（foreign_legs）を誰かに求められたら同じ ODbL で渡せるようにしておく
- **adsb.im**：今回は使っていない（経路の問い合わせを毎晩するのはやめた）。海外の空港の側が分からないのはこのため。条件はまだ読めていない（前からの持ち越し）
- adsb.lol の作者への連絡：回数が増えないので、今回のぶんでは要らない（11/7 からの問い合わせの返事待ちはそのまま）

## 5. 次にやること（本人に決めてほしいこと）
1. **表の大きさ**：海外の会社の便は1日に約1,000〜1,500回の見込み（成田・関西・羽田の国際線が中心）。1行に索引を合わせて約250バイトなので、**1年で約100〜140MB**。無料のプランの 500MB に対して大きい。本番の数を `docs/pm/foreign-collect-check.sql`（読むだけ・前の日1日）で数えてほしい。多ければ、400日より前を今の cold-archive と同じくファイル置き場に移す（消さない）案を足す
2. **乗る便に選んだ海外の便の見張り（案A）**：この記録の上に作れる。今の通知の仕組みは flight_schedule の行から始まるので、(a) flight_schedule に「推定・定刻なし」の行を入れる か (b) 小さな表 foreign_watch を別に作る かを選んでほしい（どちらも移行と RLS）。出せるのは、飛んでいる間の「いつもより○分遅い（推定）」・成田の門限の10分前より遅い見込み・ダイバート・引き返し。出発前の遅れと欠航は出せない
3. **日本の会社でも ODPT にない会社**（スカイマーク・ピーチ・ジェットスター・ジャパン・ZIPAIR・春秋航空日本など）：今回は「海外の会社」だけにした（日本の会社と JA の機体は入れない）。同じ仕組みで入れられるので、入れるか決めてほしい
4. 画面に「いつもより○分遅い（推定）」を出すなら、デザイン担当の画面案から（チェックイン担当への依頼は画面案のあと）
