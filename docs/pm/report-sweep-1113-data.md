## 3. 見つけたこと
- **開いた直後の app_status・airport_notices・current_events（1.0〜1.6秒）**：中身はどれも小さい表を読むだけ（運営の切り替え4つ・お知らせ300件まで・催し）で、データベースの中は数ミリ秒のはず。時間の大部分はデータベースの外（アメリカから東京への距離・最初のつながりを作る時間・同時に出る呼び出しの順番待ち）と見ている。①の SQL で平均ms を見れば分かる。日本から測るともっと短い見込み。まとめて1回で返す関数（例 app_boot）にすれば3往復が1往復になるが、アプリ側の直しが要るので案だけ（下の 4）
- **special_now（2.99秒）・ga_recent（2.31秒）**：special_now は15分以内に見えた特別塗装機（数十行）を seen_at の索引で、ga_recent は空港・時刻の索引で引いていて、データベースの中は軽い。同時に14本出る順番待ちの分が大きいと見ている。直していない
- **airport_tracks（3.24秒）**：1日の羽田の線を最大3,000本（1本 4,000字まで）まとめて返すので、返す量が大きい（数百KB〜MB の見込み）。④の SQL で量を測ってほしい。返す形を変える直し（線を間引く・時間で分けて返す）は画面側の読み方も変わるので、運用予想担当と決める
- **livery_board 4回同時・見方を変えるたびに取り直し・選んでいない見方の分も取る**：データの持ち場の外（運用予想・チェックイン）。下の依頼に書いた
- 前の報告で「airport-traffic は置き場を足さない」と書いたが、見回りで見る人の呼び出しが 4.07秒と一番遅く、呼ばれるたびに書き込みもしていたので、今回足した
