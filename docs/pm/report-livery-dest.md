PM の指示（11/21 14時40分）。土曜で定期の回として呼ばれたが、PM の積んだ急ぎの指示があったのでこちらをした。

## 作業の前の3行

- 手順：空港ごとの答えの着陸・離陸を、滑走路の向き・最終進入の範囲・高さで絞る → 1機が2つ以上の空港で着陸になったら、便名の行き先＞最終進入に乗っている近い方＞はっきり近い方で1つに決める（決められなければ知らせない）
- 確かめ方：羽田と成田の円が重なる場面のテスト（deno test）・全部の deno テスト・deno check・本番は読むだけの SQL で今日の成田の知らせを見る

## 原因
PM の見当どおり。recordLiveries が空港ごとの答えを順に回して `near.set(reg, …)` を上書きしていた。羽田（60海里）と成田（40海里）の円は重なり、羽田へ降りる機体も成田の円の中で高度を下げているので成田の答えでも「着陸」になり、後に回る成田で上書きされていた。成田の答えでは「ほかの空港へ向かう機体を除く」決まりがあったが、**機体から40km以内の空港しか比べていなかった**ため、羽田から40km以上離れた千葉・茨城の上の羽田行きは除かれていなかった。

## 作ったもの
1. `_shared/arr_dest.ts`（取得と分けたテストしやすい関数）
   - `refinePhases`：空港ごとの答えの arr/dep を絞る。着陸は「この空港の最終進入（延長線の横3km・手前25km・向き30°以内・3°の進入の1.6倍＋1,500ft より低い）に乗っていればそのまま」「ほかの空港の最終進入に乗っていれば外す」「この空港には高すぎて、ほかの空港なら高すぎないなら外す」「向き・距離の点が110km以内のほかの空港のほうが1割以上小さければ外す」。離陸も同じ考え方（離陸の上昇の範囲）
   - `pickAirport`：便名の行き先（時刻表）が分かれば、候補の中にあればそれ・なければ知らせない。次に最終進入に乗っている候補の近い方。どれにも乗っていなければ、候補1つで50km以内／2つ以上でいちばん近いのが2番目の7割以下の距離ならそれ。それ以外は知らせない
2. `airport-traffic`：
   - build（見る人の答え・記録の処理の答えの両方）で `refinePhases` を通す → **成田の運用タブの一覧に羽田行きが「着陸」と出にくくなる**。撮影の知らせ（着陸の数分前）・ゴーアラウンド・滑走路の学習も同じ答えを使うので、同じ取り違えが減る
   - recordLiveries の空港の決め方を `nearAirports` に。時刻表（flight_schedule、索引 flight_std あり）を引くのは、候補が2つ以上か最終進入の外の特別塗装機だけ（1回に多くても数便、200行まで）
   - 近くの空港（神戸・丘珠・佐賀・北九州・岩国）は滑走路の表（jp_runways.json）を使う。横田・小牧は表がないので位置だけ
3. 表・移行・RLS は変えない（移行とテストの番号は使っていない）。チェックイン・経営のコードには触っていない。画面（運用タブ）は返す形が同じで、着陸・離陸の札が付く機体が減るだけ

## 確かめた結果
- 新しいテスト arr_dest_test.ts 9本：羽田34L・22の最終進入の機体は成田の答えで着陸にならない／成田34L の最終進入の機体は羽田の答えで着陸にならない／成田の東で 11,000ft のまま羽田へ降りる機体は成田の着陸にならない／成田16R へ北から降りる機体は成田の着陸のまま／羽田05 から上がる機体は成田の離陸にならない／1つに決める順番（行き先が羽田なのに成田だけ→知らせない、など）
- deno test 全部 291本 通過（前の 282本＋9本）・deno check 通過・deno lint は前からの4件だけ
- 残る弱いところ：時刻表にない便（海外の会社など）で、成田のすぐ東を 7,000ft くらいで南西へ降りていく羽田行きは、形だけでは成田の着陸と見分けられない（成田の一覧に出ることがある）。知らせは時刻表で行き先が分かる便なら止まる
