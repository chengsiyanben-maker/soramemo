# 週ごとに見る数字と、その見方

毎週月曜の朝に、前の週（月〜日）の数字を下の表に書く。お金のかかる道具は使わず、Instagram のインサイト（プロアカウントなら見られる）と Supabase の SQL Editor だけで見る。

## 見る数字

**流れ**：見られる（フォロワーの外に届く）→ 人に送られる・最後まで見られる → プロフィールに来る → リンクを押す → 登録 → 最初のチェックイン

いまの Instagram は、フォロワーの外に届くかを「送信（DM でのシェア）」と「見た時間」で決めている（11/12 PM の分析）。なので上の3つをいちばん先に見る。

| # | 数字 | どこで見るか | 何が分かるか |
|---|---|---|---|
| 1 | **送信（シェア）数**（投稿ごと） | 投稿のインサイト（紙飛行機の数） | 人に送りたくなったか。**いちばん大事** |
| 2 | **リールの平均視聴時間**（と最後まで見た割合が出ていればそれも） | リールのインサイト | 冒頭で離れていないか。台本の長さの半分を下回ったら冒頭を変える |
| 3 | **トライアルリールの結果**（版ごとのリーチ・平均視聴時間・送信） | トライアルリールのインサイト | どの冒頭が伸びたか。伸びた版を「フォロワーにも共有」する |
| 4 | リーチ（投稿ごと・週の合計。フォロワー以外の割合も） | インサイト → 投稿 | どれだけの人に届いたか、外に出たか |
| 5 | 保存数 | 投稿のインサイト | 「あとで使う」と思われたか（カルーセルで見る） |
| 6 | プロフィールへのアクセス | インサイト → 概要 | 投稿から興味を持たれたか |
| 7 | 外部リンクのタップ（プロフィールのリンク） | インサイト → 概要 | 登録しようとした人の数（いちばん近い数字） |
| 8 | リンクのスタンプのタップ（ストーリーズ） | ストーリーズのインサイト | ストーリーズから登録しようとした人 |
| 9 | 新規登録数 | Supabase（下の SQL ①） | 実際に登録した人 |
| 10 | 7日以内に1回以上チェックインした人 | Supabase（下の SQL ②） | 登録したあと使い始めたか |
| 11 | フォロワーの増え方 | インサイト | 次の投稿が届く人が増えているか |
| 12 | コラボ投稿のリーチ（相手のフォロワーへの分） | コラボ投稿のインサイト | 声かけが効いたか（[reach.md](reach.md)） |

### ほかの場所（X・Threads・YouTube ショート）の数字

出し始めたら、同じ週の行に足す。手間をかけないため、見るのは各2つだけ。

| 場所 | 見る数字 | どこで見るか |
|---|---|---|
| X | 表示回数・リンクのクリック | 投稿の「アナリティクス」 |
| Threads | 閲覧数・再投稿／シェア | 投稿の下の数字・インサイト |
| YouTube ショート | 視聴回数・平均視聴率（または維持率） | YouTube Studio の動画ごとの数字 |

## 見方

- **最初の週の数字を基準にする**。よその平均とは比べない（アカウントの大きさで全く変わるため）
- **割合で見る**
  - 1 ÷ 4（届いた人のうち送った割合）を投稿どうしで比べる。高かった形（送る相手が思い浮かぶ中身）を次の週も続ける
  - 6 ÷ 4（届いた人のうちプロフィールに来た割合）が下がった → 1枚目・冒頭の見出しが弱い。1枚目を変える
  - 7 ÷ 6（来た人のうちリンクを押した割合）が下がった → プロフィールの文が弱い。プロフィールの1行目に「空港で印を集める非公式アプリ・アーリーアクセス中」を入れる
  - 9 ÷（7＋8）（押した人のうち登録した割合）が低い → 登録の途中で止まっている。コードのメールが届いているか、登録の画面で迷っていないかを確かめる（アプリ側）
  - 10 ÷ 9 が低い → 登録しても空港に行く用事がない人が多い。旅の前の時期（年末年始）に向けた投稿を増やす
- **送信と保存は投稿どうしで比べる**。いいねの数では決めない
- **500人に向けて**：週の登録数を足していき、4週目の終わりに何人まで来たかを見る。足りない分を、5週目からの投稿の回数ではなく中身（どの形が登録につながったか）で埋める
- **登録が多すぎるとき**：投稿のあと1時間の登録が80人を超えたら、その日はリンクのスタンプを足さない（コードのメールの上限が1時間100通のため。[rules.md](rules.md)、SQL ④）

## Supabase の SQL Editor で見る（読むだけ）

① 週ごとの新規登録数（日本時間の月曜はじまり）

```sql
select date_trunc('week', created_at at time zone 'Asia/Tokyo')::date as 週,
       count(*) as 登録
from auth.users
where created_at >= '2026-10-30'
group by 1 order by 1;
```

② 登録した週ごとの、7日以内に1回以上チェックインした人

```sql
select date_trunc('week', u.created_at at time zone 'Asia/Tokyo')::date as 週,
       count(*) as 登録,
       count(*) filter (where exists (
         select 1 from public.checkins c
         where c.user_id = u.id
           and c.created_at < u.created_at + interval '7 days'
       )) as 七日以内に使った人
from auth.users u
where u.created_at >= '2026-10-30'
group by 1 order by 1;
```

③ 1日ごとの登録数（告知した日に増えたかを見る）

```sql
select (created_at at time zone 'Asia/Tokyo')::date as 日, count(*) as 登録
from auth.users
where created_at >= now() - interval '14 days'
group by 1 order by 1;
```

④ 1時間ごとの登録数（投稿の日に、上限の1時間100通に近づいていないかを見る）

```sql
select date_trunc('hour', created_at at time zone 'Asia/Tokyo') as 時間, count(*) as 登録
from auth.users
where created_at >= now() - interval '2 days'
group by 1 order by 1;
```

- 運営者自身やテスト用のアカウントは、分かっていれば `where` で外す
- この SQL は数えるだけで、表を変えない。アプリのコードにも入れない
- 今は「どの投稿から来た人か」は分からない。分かるようにするにはアプリ側の仕組みが要る（`docs/pm/report-ads-early-access.md` の依頼）
