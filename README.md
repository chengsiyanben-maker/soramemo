# そらメモ（サーバー版）

国内86空港でチェックインして印と路線を集める位置情報ゲーム。チェックインの判定と記録はサーバー（Supabase）で行う。

## サーバーがやること

- 端末は「位置・誤差・位置を取った時刻」だけを送る。空港・ターミナルの判定、フライトの成立、記録はサーバーが行う
- フライトの時刻は端末の時計ではなく、サーバーが受け付けた時刻で計算する
- 利用者は自分の記録を読めるだけで、チェックインとフライトを書き込めない（行レベルセキュリティ）
- 旅客機でも不可能な速さの移動は、フライトにせず `impossible_speed` の印を付けて残す
- 電波がなくて送れなかったチェックインは端末に保留し、つながったら古い順に送る（`queued: true`）。保留分は端末が位置を取った時刻で判定し、24時間以内のものだけ受け付けて `offline` の印を付ける。新しいチェックインを送る前に保留分を先に送る
- フライトの航空会社と便名は、本人だけが `set_flight_airline` 関数で設定できる（フライトそのものは書き換えられない）
- 会社経営（資金・増便・役職・収益の受け取り）はサーバーで計算する。利用者は `co_state` `co_collect` `co_upgrade` `co_set_role` `co_rename` `co_buy` `co_assign` `co_build` の関数だけを使え、資金を直接書き換えられない。数値を変えるときは、このSQLとアプリの `ECON` の両方を同じ値にする

## 航空会社の表示について

航空会社名と便名は、利用者が乗ったフライトの事実として文字だけで表示する。ロゴ、会社の色、機体デザインは使わない。テーマ名や宣伝に航空会社名を使うこと、公式・提携と受け取れる表現は、各社と提携するまで行わない。

### 3. チェックインの処理を公開する

パソコンがない場合（ダッシュボードで作る）：

1. 左のメニューの「Edge Functions」→「Deploy a new function」→「Via Editor」
2. 関数名を `checkin` にする
3. `tools/dashboard/checkin.ts`（`python3 tools/make_dashboard_checkin.py` で作る） の中身を全部貼り付けて「Deploy」

パソコンがある場合（CLIで公開する）：

```
npx supabase login
npx supabase link --project-ref <プロジェクトID>
npx supabase functions deploy checkin
```

### 4. ログインの設定

1. 「Authentication」→「URL Configuration」を開く
2. 「Site URL」と「Redirect URLs」に、アプリを公開するURL（例：`https://<ユーザー名>.github.io/<リポジトリ名>/`）を入れる
3. 自前のメール送信（SMTP）を設定してから、「Authentication」→「Emails」の「Magic link or OTP」と「Confirm signup」の本文に、6桁のコード `{{ .Token }}` を入れる（例：「そらメモのログイン用のコード：{{ .Token }}」）。今のSupabaseは、SMTPを設定しないと文面を書き換えられず、標準のメール送信はプロジェクトのメンバーにしか送れない。手軽なのは、そらメモ専用のGmailの「アプリ パスワード」を使う方法（Host `smtp.gmail.com`、Port `465`）。iPhone でホーム画面に追加したアプリは、メールのリンクだと Safari 側でログインしてしまうため、コードを使う
4. メールでのログインは最初から有効になっている。ただし標準のメール送信は1時間あたりの回数が少ないため、アーリーアクセスの前に「Authentication」→「SMTP Settings」で独自のメール送信サービスを設定する

### 5. アプリにサーバーの場所を入れる

1. 「Project Settings」→「API」を開き、「Project URL」と「anon public」キーをコピーする
2. `web/config.js` に入れる（アプリと運営画面の両方がこのファイルを読む。anon キーは公開して問題ない種類のキー。`service_role` キーは絶対に入れない）

```js
window.SORAMEMO_CONFIG = { supabaseUrl: "https://xxxx.supabase.co", supabaseAnonKey: "eyJ..." };
```

### 6. アプリを公開する

`web/` の中身を GitHub Pages などで公開する（手順は前と同じ）。公開したURLを開き、メールアドレスを入れて届いたリンクを押せばログインできる。

## 経済バランスのシミュレーション

```
python3 tools/economy_sim.py
```

4タイプの利用者（月1往復のライト〜月10往復の修行）が2年間遊んだときの、収益と節目（初の機材、評判の星、機材の解放）の時期を出す。数値を変えるときは、このスクリプト、アプリの `ECON`、SQLの関数の3か所を同じ値にする。

## そらメモ＋（月額500円）の準備

有料機能は「年間まとめ」と「過去フライトの一括取り込み」。決済は Stripe を使う。加入状態は Stripe からの通知でだけ書き換わり、利用者は自分で加入状態を変えられない。

1. https://stripe.com でアカウントを作り、「商品」で「そらメモ＋」を作って、価格を「月額500円（継続）」にする。表示される価格ID（`price_...`）を控える
2. Supabase の「Edge Functions」→「Secrets」に次の4つを登録する
   - `STRIPE_SECRET_KEY`：Stripe の「開発者」→「APIキー」のシークレットキー（最初はテスト用の `sk_test_...`）
   - `STRIPE_PRICE_ID`：手順1の価格ID
   - `SITE_URL`：アプリを公開したURL（例：`https://<ユーザー名>.github.io/<リポジトリ名>/`）
   - `STRIPE_WEBHOOK_SECRET`：手順4で表示される `whsec_...`
3. Edge Function を3つ公開する（CLI：`npx supabase functions deploy plus-checkout plus-portal` と、通知用は `npx supabase functions deploy plus-webhook --no-verify-jwt`）。通知用の `plus-webhook` は、Stripe からの通知にログインの印が付かないため、JWTの確認を切って公開する（代わりに Stripe の署名を確かめている）
4. Stripe の「開発者」→「Webhook」で、送信先に `https://<プロジェクト>.supabase.co/functions/v1/plus-webhook` を登録し、イベント `checkout.session.completed` `customer.subscription.created` `customer.subscription.updated` `customer.subscription.deleted` を選ぶ
5. Stripe の「設定」→「カスタマーポータル」を有効にする（解約・支払い方法の変更に使う）
6. まずテスト用のキーとテスト用のカード（4242 4242 4242 4242）で申し込み・解約を試し、問題なければ本番のキーに切り替える

注意：特定商取引法にもとづく表記は `web/tokushoho.html` にひな形がある。黄色の欄を埋めてから公開する。

## 便の照合（運航確認）

毎晩1回、前日以前（7日以内）の未確認のフライトを、OpenSky Network の到着記録と照らし合わせる。出発の推定空港・着陸時刻・コールサイン（便名を記録していれば）が合えば「運航確認済み」、その空港の到着記録が1件もなければ「運航データなし」にする。当てはまる便がないものは3回まで試す。照合のルールは `supabase/functions/_shared/verify.ts`。

1. https://opensky-network.org でアカウントを作り、API用のクライアント（client_id と client_secret）を作る
2. Supabase の「Edge Functions」→「Secrets」に `OPENSKY_CLIENT_ID` `OPENSKY_CLIENT_SECRET` と、長いランダムな文字列の `CRON_SECRET` を登録する
3. `npx supabase functions deploy verify-flights --no-verify-jwt` で公開する（`x-cron-secret` が合わない呼び出しは断る）
4. 「Database」→「Extensions」で `pg_cron` と `pg_net` を有効にし、`20261004000008_verify.sql` の最後にある例のとおり、毎晩の実行を登録する

OpenSky の無料枠は1日4,000クレジットで、1回の問い合わせは4クレジット。1晩に最大200件まで照合する（同じ空港・同じ時間帯はまとめて1回）。ODPT（時刻表からの便名の候補表示）は、開発者登録のあとに追加する。

## 運営用の確認画面

運営コンソール（`ops-console/index.html`）を開くと、利用者数などの数字と、印の付いたチェックイン（不可能な速さ・誤差大・電波なしで保留）の一覧が見られる。「問題なし」で印を外し、「取り消す」でそのチェックインと、それを使ったフライトを消す。操作は `admin_actions` 表に理由つきで残る。

1. `ops-console/config.js` に、アプリと同じ値を入れる
2. 自分のメールアドレスでアプリに一度ログインしてから、SQL Editor で運営者として登録する
   `insert into ops.admins (user_id) select id from auth.users where email = '<運営者のメールアドレス>';`
3. メールの本文に6桁のコードが入っているか確かめる（「4. ログインの設定」の手順3）
4. 手元のパソコンで `ops-console/index.html` をブラウザで開き、メールに届いた6桁のコードでログインする
5. 初回は2段階認証の設定になる。認証アプリ（Google Authenticator など）でQRコードを読み取り、表示された6桁のコードを入れる

運営者として登録していない人は、ログインしても何も見られず、操作もできない。2段階認証の前の運営者も同じ。

## 運営のための情報集め

個人を特定しない形で、次の4つを集めて運営コンソール（`ops-console/index.html`）に表示する。

| 見出し | 中身 | 元の情報 |
| --- | --- | --- |
| 利用状況 | 日ごとの利用者数・チェックイン・新規登録・アプリを開いた起動、7日・30日の利用者、続けて使う人の割合、人気の空港・路線、そらメモ＋の加入と解約 | 今ある記録（新しくは集めない） |
| 使われ方 | 開いた画面、使った機能、チェックインの成否などの回数、端末の種類 | `usage_events`（利用者IDなし、起動ごとの使い捨ての番号） |
| エラー | アプリのエラー、チェックインが断られた理由 | `client_errors`、`checkin_rejections`（どちらも利用者IDなし。断られた記録は座標も持たない） |
| 判定の見直し | 空港ごとのチェックイン地点の距離の分布・誤差、惜しい範囲外の回数 | 今ある記録と `checkin_rejections` |

- アプリの「設定」→「使われ方とエラーを送る」で、利用者は送らないようにできる
- 使われ方とエラーは180日、断られたチェックインは1年で消す。`20261004000011_insights.sql` の最後にある例のとおり、`insights_cleanup` を毎日実行するよう登録する
- プライバシーポリシー（`web/privacy.html`）に、集める内容と送らない設定を書いてある
- サーバー版では、チェックインの範囲・誤差の判断をサーバーに任せる（端末で先に断らない）。断った理由を記録して、判定の見直しに使うため

## エアライン経営の公開

アーリーアクセスはスタンプラリーだけで始め、エアライン経営は後で公開する。

- 公開前は、アプリに「スタンプラリー｜エアライン経営」の切り替えも、設定の経営の項目も、印の画面の守り神との出会いも出ない。会社の関数（資金・増便・機材・施設など）は、運営者以外は使えない（`game not released`）
- 公開前でも、デモモードでは経営を試せる。運営者は自分のアカウントでも試せる
- 公開するときは、運営コンソールの「非常停止」の見出しにある「エアライン経営を公開する」をオンにする。アプリを公開し直す必要はなく、利用者が次にアプリを開いたときに出る
- 公開前のチェックインとフライトも記録されているので、公開したときは、それまでに飛んだ路線と出会った空港から会社が始まる
- サーバーを使わない版は、`web/config.js` の `gameReleased` で切り替える

## ステータスの先読み（そらメモ＋）

記録タブの「ステータスの目安」の下。無料は今のポイントと、次の段階までの残り（ANA・JAL）。そらメモ＋ は次の2つ。

- 到達の予測：今年の1月1日からのペースで、各段階に何月何日ごろ届くか。年内に届かなければ、年末の見込みと足りない分
- あと何回：路線と運賃を選ぶと、1区間のポイントと、各段階までその区間をあと何回（何往復）か。初期値は、いちばんよく乗っている路線と運賃。JAL は JGC入会（Life Status 1,500）までの回数も出す
- JAL の段階：クリスタル 30,000／サファイア 50,000／JGCプレミア 80,000（2026年。JGC会員のみ）→ 2027年の搭乗分から JMBプレミア（搭乗実績だけで達成）／ダイヤモンド 100,000（FOP の条件。回数による条件は計算に入れていない）
- そらメモ＋ は月額500円と年額4,800円。年額は Stripe に年額の価格を作り、その ID を `STRIPE_PRICE_ID_YEAR` に入れると申し込めるようになる

## 羽田の今の運用

ホームの「羽田の今の運用」から開く。気象通報（METAR）から北風／南風／南風（都心ルート）を推定し、着陸・離陸の滑走路と、着陸の滑走路の最終進入（延長線上の約10海里）を国土地理院の地図に描く。手で運用を切り替えることもできる。

- 気象通報は `supabase/functions/metar`（中継）を通して読む。配信元（aviationweather.gov）はほかのサイトのアプリから直接読めないため。同じ空港の通報は5分間使い回す。ログインは不要
- 推定のルール：34滑走路（真方位330°）への追い風が7ノットを超えたら南風。南風で15時〜19時、視程5,000m以上なら都心ルート。南風で視程5,000m未満は直線の計器進入（ILS）
- 都心ルートの離陸の使い分け（16L＝長距離の国際線、16R＝北日本方面、22＝西日本・南西方面）は、運営者の知識にもとづく
- 滑走路の端と、着陸が始まる位置（ずらした接地点）は OurAirports の滑走路データ。地図の部品は Leaflet（jsDelivr から読み込み）
- 曲がった進入経路（LDA・RNP・海ほたる経由など）は、まだ描いていない。ウェイポイントの座標は、航空路誌（AIP Japan）の RNAV ウェイポイントの一覧（チャート）の値をそのまま入れる。推測した座標では描かない
- 画面には「推定であり、実際の運用は管制の指示で変わる。航法には使えない」と出している
- 無料と そらメモ＋ の分け方：無料は運用の推定とその理由（数字なし）、使っている滑走路、滑走路の地図、運用の手動切り替え。そらメモ＋ は気象通報の詳しい値（風向・風速・視程、34滑走路への追い風）、地図の進入・離陸の線、曲がった進入経路（追加予定）。判定はアプリの `plusOn()`（デモモードではお試しできる）

## 番外編：自衛隊・米軍の飛行場、滑空場、飛行場

- 自衛隊・米軍の飛行場30か所、滑空場33か所、飛行場30か所（定期便のない公共用の空港10か所と、ホンダエアポート・大利根飛行場・福島スカイパーク・北海道の農道空港などの民間の飛行場20か所）。番外編かどうかは `airports.extra_kind`（mil / glider / field）で見分ける。超軽量機・パラグライダーの離着陸場は、立ち入れるかがはっきりしないので入れていない。位置は OurAirports（パブリックドメイン）から取り、日本語の名前を付けた。名前と位置はアーリーアクセスで確かめて直す
- 民間の86空港とは別の図鑑（図鑑タブの最後の「番外編」）で、全国制覇・地方制覇・空港の数には数えない。実績は「番外編：基地」「番外編：滑空場」に各5つ
- チェックインの判定では民間空港を優先する（千歳基地と新千歳空港、大村航空基地と長崎空港は判定範囲が重なる）。これらとの間はフライトとして記録しない。守り神・経営の対象にもしない
- 基地は判定範囲を1.5〜2kmにして、フェンスの外（公道・公園・展望できる場所）から押せるようにした。印の画面に「基地の中には入れません」「ドローンは飛ばさない」などの注意を出す。滑空場（判定範囲800m）には「飛行中は滑走路に入らない」と出す
- 硫黄島・南鳥島は一般の人が行けないので入れていない。民間と共用の飛行場は民間空港として入っている
- 足したり直したりするときは、アプリ（`src/index.html` の `EXTRA_RAW`）とデータベース（`airports` の extra_kind がある行）の両方を同じ内容にする

## 搭乗券の読み取り・写真に印を押す・ステータスの目安

- 搭乗券の読み取り：記録タブの「搭乗券を読み取る」（カメラ）か「画像から読み取る」。IATA の BCBP 規格のバーコード（PDF417・QR・Aztec）を、ZXing（jsDelivr から読み込み）か端末の BarcodeDetector で読む。使うのは区間・航空会社・便名・日付・座席だけで、名前と予約番号は保存しない。記録済みのフライトには付け、まだ飛んでいない便は「搭乗予定」として端末に覚え、フライトが記録されたときに自動で付ける（3日で忘れる）。記録のない過去の便は記録帳に追加できる
- 写真に印を押す：印の画面とフライトの画面の「写真に押す」。写真は端末の中だけで処理する
- ステータスの目安：記録タブの「ステータスの目安」。ANA プレミアムポイント（2026年5月19日以降は新運賃、それより前は旧運賃の表）、JAL FLY ON ポイント、JAL Life Status ポイント（国内線1搭乗5）。運賃はフライトの画面で選ぶ（未選択は ANA スタンダード／旧 SUPER VALUE、JAL セイバーとして計算）。区間マイルは JAL 公開の国内線区間マイル表（2023年7月現在）にある区間はその値、ない区間は地図上の距離。表と運賃の率はアプリの `FARES` と `ROUTE_MILES` にまとまっているので、各社の制度が変わったらそこを直す
- ホーム画面に追加：Android の Chrome などはボタン1つで追加できる（beforeinstallprompt）。iPhone は手順を案内する
- テストの搭乗券の画像は `tests/e2e/make_bp_fixtures.py` が今日の日付に合わせて作る（`pip install pdf417gen segno`）

## バックアップ（自分でとる）

無料プランには毎日の自動バックアップがないので、運営コンソールの「バックアップ」から書き出す。週に1回が目安で、前回から7日以上たつと運営コンソールに知らせが出る。

- 書き出すもの：チェックイン・フライト・記録帳・会社（資金・増便・機材・施設）・加入状態・運営者・運営の切り替えと、利用者のメールアドレス（JSONファイル1つ）
- ファイルにはメールアドレスとチェックインした位置が入る。パソコンの安全な場所に保管し、人に渡さない
- 戻すとき：`python3 tools/restore_from_backup.py soramemo-backup-….json > restore.sql` でSQLを作り、SQL Editor で流す。すでにある行は上書きせず、消えた行だけが戻る（2回流しても重ならない）
- ログインのアカウント（`auth.users`）そのものは、このファイルからは作り直せない。同じプロジェクトでデータが壊れた・消えたときに戻すためのもの

## 更新のしかた（自動で反映する仕組み）

GitHub のリポジトリにこのプロジェクト全体を置くと、main に変更を入れるたびに `.github/workflows/deploy.yml` が自動で動き、次の順で反映する。途中で失敗したらそこで止まるので、SQLより先にアプリが公開されて動かなくなることはない。

1. テスト（チェックインの判定・便の照合のテストと、すべてのSQLを模擬のデータベースに流すテスト）
2. まだ流していないSQLだけを、番号順に流す（`supabase db push`）
3. サーバーの関数をすべて公開する（`supabase functions deploy`。入口での確認の設定は `supabase/config.toml`）
4. アプリを作って公開する（`node tools/build.mjs` → GitHub Pages）

アプリには版の番号が自動で付き、設定の画面のいちばん下に出る。アプリを開いている間に新しい版が公開されると、「新しい版が届きました」と出る。

### はじめに1回だけ

1. リポジトリの中身を、このプロジェクト全体に置き換える（GitHub Desktop を使うと簡単。前のアプリの部品だけのファイルは消してよい）
2. リポジトリの「Settings」→「Pages」で、Source を「GitHub Actions」にする
3. 「Settings」→「Secrets and variables」→「Actions」で次を登録する
   - Variables：`SUPABASE_PROJECT_REF`（プロジェクトのID）
   - Secrets：`SUPABASE_ACCESS_TOKEN`（Supabase の「Account」→「Access Tokens」で作る）、`SUPABASE_DB_PASSWORD`（データベースのパスワード。忘れたら「Project Settings」→「Database」で作り直せる。アプリには影響しない）
4. 「Actions」で「初回だけ：手で流したSQLを記録」を選び、最後に SQL Editor で手で流したSQLの番号（例：`20261004000014`）を入れて「Run workflow」を押す
5. 「Actions」で「反映」を選び、「Run workflow」を押す（以後は main に変更を入れるだけで動く）

### ふだん

変わったファイルを GitHub に入れる（GitHub Desktop なら「Commit」→「Push」）。「Actions」の画面で、緑のチェックが付けば反映済み。赤い×なら、その手順を開くと理由が出る。

### 手で反映するとき（自動の仕組みを使わない場合）

SQL は `supabase/migrations/` を番号順に SQL Editor で流す。checkin 関数をダッシュボードに貼るときは `python3 tools/make_dashboard_checkin.py` で `tools/dashboard/checkin.ts` を作って貼る。

## 攻撃への備え

### 仕組み（`20261004000012_hardening.sql` と Edge Function）

| 種類 | 内容 |
| --- | --- |
| 分離 | 運営者の名簿、操作の記録、使われ方・エラー・断られたチェックインの記録、回数制限、非常停止の状態は、APIに出ない `ops` スキーマにある。RLSの設定を誤っても外から直接は触れない。外から使えるのは決まった関数だけ |
| 運営コンソールの分離 | 運営コンソールは公開サイト（`web/`）に置かない。運営者の手元で開く。ログインは6桁のコードで、新しいアカウントは作らない |
| 運営者の2段階認証 | 運営の関数はすべて、認証アプリのコードまで確かめたログイン（aal2）でないと動かない |
| 回数制限 | チェックイン 1人1分20回、使われ方の送信 1起動1分6回・全体1分3,000回、エラー 1起動1時間10件・全体1分600件、そらメモ＋の申し込み 1人10分5回、管理画面 1人10分10回、アカウント削除 1人1時間3回。データベースで区切りごとに数える |
| 巻き添えにしない | 断られたチェックインの記録は、チェックインの応答を待たせずに行い、失敗しても無視する。記録の受け口が詰まっても、チェックインは止まらない |
| 非常停止 | 運営コンソールの「非常停止」から、メンテナンス中の表示・チェックインの一時停止・記録の停止を切り替える。アプリは起動時に読み、チェックインの停止は30秒以内に反映 |
| ページの防御（CSP） | 配る用の `web/index.html` には、ページに書いたスクリプト（ハッシュで指定）と決まった配信元（部品の配信元、Turnstile）だけを動かす設定が入っている。差し込まれたスクリプトや、HTMLに直接書いた onclick は動かない |
| ロボット除け | ログイン用のメール送信に CAPTCHA（Cloudflare Turnstile）をかけられる。メールの送信枠を使い切られたり、他人に大量のメールを送りつけられたりするのを防ぐ。確認の合図は1回ごとに使い捨て |
| 合言葉 | 夜間の照合（verify-flights）の合言葉は、比べる時間から中身を推測されない比べ方をする |

### Supabase で設定しておくこと

- 「Authentication」→「Rate Limits」：メール送信・ログインの回数制限を、標準より厳しめにする
- 「Authentication」→「Attack Protection」：CAPTCHA を有効にする。Cloudflare の管理画面で Turnstile のサイトを作り（ドメインに公開先と、運営コンソールを開く場所を入れる）、シークレットキーを Supabase に、サイトキー（公開鍵）を `web/config.js` と `ops-console/config.js` の `turnstileSiteKey` に入れる。サイトキーを入れたときだけ、アプリと運営コンソールのログインに確認の部品が出る（多くの人は何も操作せずに通る）
- 「Authentication」→「Multi-Factor」：TOTP（認証アプリ）を有効にする（運営コンソールで使う）
- 「Database」→「Backups」：毎日のバックアップを確認する。可能なら時点復元（PITR）を有効にする
- `service_role` キーは Edge Function の中だけで使い、アプリや運営コンソールには絶対に入れない。漏れたと思ったらすぐに作り直す
- 運営者のメールアカウントにも2段階認証を入れる

### 攻撃を受けたときの手順

1. 運営コンソールの「非常停止」で、まず被害を止める
   - 記録の受け口が大量に叩かれている → 「使われ方・エラーを記録する」をオフ
   - 偽のチェックインが大量に来る → 「チェックインを受け付ける」をオフ（必要なら「メンテナンス中にする」）
2. 「印付き」「エラー」「使われ方」で、何が起きているかを確かめる
3. 不正なアカウントを特定したら、Supabase の「Authentication」→「Users」で利用停止または削除する。不正なチェックインは「印付き」から取り消す
4. 鍵が漏れた疑いがあれば、Supabase の「Project Settings」→「API」で作り直し、`web/config.js` と Edge Function の Secrets を差し替える
5. 落ち着いたら、非常停止を元に戻す

## ログイン前の記録の引き継ぎ

サーバーを使う前に端末の中だけで遊んでいた人がログインすると、ホームに「ログイン前の記録があります」と出る。「記録帳に引き継ぐ」を押すと、端末のフライトと記録帳を、アカウントの記録帳（`manual_flights`）に入れる（同じ区間・同じ日のものは重ねない）。端末の中だけで付けた印（チェックイン）は、サーバーで確かめられていないため引き継がない。印として引き継げると、位置の判定を通らずに印を増やす抜け道になるため。

## アカウントの削除

`delete-account` も公開する（`npx supabase functions deploy delete-account`）。アプリの「設定」→「アカウントを削除」から呼ばれ、加入中なら Stripe の定期支払いを止めてから、アカウントを消す。各表は `auth.users` を `on delete cascade` で参照しているので、記録もすべて消える。

## 公開前に埋めるもの

`web/privacy.html` `web/terms.html` `web/tokushoho.html` の黄色の欄（運営者名、連絡先、裁判所、バックアップの保存日数など）。ひな形なので、公開前に専門家に確認してもらう。

## アプリに手を入れるとき

`src/index.html` を直してから、配る用を作り直す。

```
cd tools && npm install terser@5 csso@5 && cd ..
pip install fonttools brotli
node tools/build.mjs
```

配る用は、原本から説明文や空白を省く。明朝体（Shippori Mincho、SIL Open Font License 1.1。`web/fonts/OFL.txt`）は Google Fonts を使わず、このアプリに出てくる文字（約840字）と英数字・記号だけを抜き出したフォント（`web/fonts/mincho-….woff2`、約160KB）を作って自前で配る。文字が増えても作り直すだけでよい。サービスワーカー（`web/sw.js`）の版の番号も中身から自動で付く。フォントを作るには `pip install fonttools brotli` が必要。2026年10月の見直しで、フォントの通信量は約1,060KBから約300KBに、アプリのファイルは圧縮配信で58KBから53KBになった。
